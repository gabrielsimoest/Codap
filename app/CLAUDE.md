Ver seção "Autenticação e sincronização" abaixo.

Requisições/mutations via `@tanstack/react-query` (`PersistQueryClientProvider` em `App.tsx`, não o `QueryClientProvider` puro — ver "Cache persistente" abaixo). Devtools do React Query: `react-native-react-query-devtools` (`DevToolsBubble`, componente `src/components/dev/QueryDevTools.tsx`, renderizado só quando `__DEV__` — nunca em produção), usa `expo-clipboard` para copiar dados do cache.
- **Cache persistente de queries**: `src/services/queryPersister.ts` (`@tanstack/query-async-storage-persister`, sobre `AsyncStorage`) + `gcTime: Infinity` nas queries por padrão (`queryClient.ts`) — sobrevive a um kill do processo, ao contrário do cache padrão do React Query (só em memória). Primeiro uso real: `useAreasQuery`/`useModulesQuery` (`src/hooks/queries/`), que também passam `staleTime: Infinity` (cache **nunca** expira sozinho — revalidação só quando alguém invalidar a query, e quem faz isso é `useContentVersionSync`, comparando a tabela `content_version`; ver "Conteúdo de aulas"). SQLite nunca guarda esse conteúdo — ficaria redundante com o cache do próprio React Query.
- Detecção de conectividade: `@react-native-community/netinfo`.
- **Barra de navegação do Android escondida por padrão** (`expo-navigation-bar`): `<NavigationBar hidden style="auto" />` no `App.tsx` a esconde, e um deslize na borda de baixo a mostra por ~2 s (comportamento "transient bars by swipe" do módulo). Quando aparece, segue o **tema do aparelho**: `userInterfaceStyle` é `"automatic"` no `app.json` (era `"light"`, o que deixava a barra de 3 botões branca num app escuro) e o `style="auto"` escolhe a cor dos botões. O plugin `["expo-navigation-bar", { "hidden": true }]` só vale em build nativo; no Expo Go quem esconde é o componente. **Mudar `userInterfaceStyle` exige reiniciar o Metro** (o manifesto é lido na partida). No primeiro uso o Android mostra uma vez o aviso "Viewing full screen"; é do sistema e não se evita. No iOS o componente não faz nada. Para testar no emulador: `adb shell cmd overlay enable com.android.internal.systemui.navbar.threebutton` (e `...gestural` para voltar).
- **Notificações locais**: `expo-notifications` (plugin em `app.json` com cor `#5469D3` e canal padrão `reminders` — **exige novo build nativo**). **Não funciona no Expo Go do Android**: o pacote exige o módulo nativo `ExpoTopicSubscriptionModule` já no import e o Expo Go 57.0.9 (a versão mais nova para o SDK 57) não o tem — um `import` estático derrubaria o app inteiro. Por isso `NotificationService` carrega o pacote sob demanda, depois de checar o módulo com `requireOptionalNativeModule` (um `try/catch` em volta do `require` não basta: o Metro reporta a falha como erro fatal antes de a exceção chegar ao `catch`); no Expo Go o recurso fica inativo e o app abre normalmente. Para testar lembretes de verdade, use um dev build ou o app de produção. Só há lembretes de inatividade, locais e agendados — sem push remoto. Ver seção "Lembretes de inatividade" abaixo.
- **Deep linking** (`expo-linking`, `scheme: "codap"` em `app.json`) — sempre ativo (não gated por `__DEV__`), tanto para testar telas via ADB sem navegar manualmente quanto para links reais (e-mail/notificação) no futuro. Ver seção "Autenticação e sincronização" abaixo (`linking` é montado em `App.tsx` e respeita o gate de login). A rota `Lesson` (`codap://lesson/:areaId/:moduleId/:lessonId`) declara `parse: { areaId: Number, ... }` — **obrigatório**: segmentos de URL chegam como string, e um `areaId` string montaria a key `["modules", "3", "pt"]`, uma entrada de cache diferente de `["modules", 3, "pt"]` e órfã para sempre.
- i18n: `i18next` + `react-i18next`, idiomas `en`/`pt`.
- Sem suíte de testes automatizados e sem script de lint configurados no `package.json` atualmente.
- **Splash screen**: configurada via plugin no `app.json` (`plugins: [["expo-splash-screen", { image, resizeMode, backgroundColor }]]`), não mais pela chave `splash` de nível raiz — essa chave foi descontinuada (o schema do Expo passou a rejeitá-la) e o `expo-splash-screen` reescreveu sua config para plugin a partir do SDK 54; o valor padrão de `backgroundColor` do plugin é `#ffffff`, então omitir essa config faz a splash aparecer branca em vez da cor do app. A splash do app é **fundo preto com só a logo** (`icon.png`, `resizeMode: "contain"`, `imageWidth: 200`, sem título); `cover` esticaria o ícone quadrado até preencher a tela. **Isso só vale em build nativo (EAS ou build de desenvolvimento)**: no Expo Go quem aparece é a tela de carregamento do próprio Expo Go (fundo branco, ícone, nome do app e "Bundling…"), que o app não controla. A única coisa do app que o Expo Go usa nessa tela é o `expo.icon` (mais o `name`): por isso o ícone do app é `assets/app-icon.png`, **opaco e sem margem** (1024×1024, o quadrado do logo preenchendo tudo, o que a App Store exige e evita a moldura cinza que o Expo Go desenhava ao redor do `icon.png`, que tem margem transparente). O `icon.png` continua sendo o logo com margem: serve ao splash nativo, ao primeiro plano do ícone adaptativo e ao logo do login.
- **pnpm + Expo CLI**: `pnpm-workspace.yaml` define `publicHoistPattern` para `*expo*`, `*react-native*`, `@react-native/*` e `metro*`. Isso é necessário porque `@expo/cli` usa `metro-runtime` internamente sem declará-lo como dependência própria (só `@expo/metro` o declara) — em pnpm estrito (sem hoisting) isso quebra `expo start`/`expo run:*` com `Cannot find module 'metro-runtime/package.json'`. Não remova esse hoisting sem substituir por outra solução equivalente.

## Navegação

`MainNavigation.tsx` (stack, header oculto) contém `Login` → `Register` → `Home`, onde `Home` é o `TabNavigation.tsx` (bottom tabs: `Class`, `Market`, `Account`, `Settings`, cada aba com ícone via componente `Icon` e animação própria em `TabButton`).

**Rotas tipadas** (`src/types/navigation.d.ts`): `RootStackParamList` (rotas do stack raiz — `Login: {email?: string} | undefined`, `Register: undefined`, `Home: undefined`, `Lesson: {areaId, moduleId, lessonId}`) e `MainTabParamList` (as 4 abas, todas `undefined`), com uma augmentation global (`declare global { namespace ReactNavigation { interface RootParamList extends RootStackParamList {} } }`) que faz `useNavigation()`/`useRoute()` inferirem o tipo certo em qualquer lugar do app, sem passar o genérico manualmente em cada tela. `createStackNavigator<RootStackParamList>()` (`MainNavigation.tsx`) e `createBottomTabNavigator<MainTabParamList>()` (`TabNavigation.tsx`, com `TabItem.route: keyof MainTabParamList` em vez de `string`) usam esses tipos, então um nome de rota errado em `<Stack.Screen name="...">`/`<Tab.Screen name="...">` já não compila. `useNavigate` (`src/hooks/useNavigate.ts`) envolve `useNavigation<StackNavigationProp<RootStackParamList>>()` (do `@react-navigation/stack` — o pacote realmente instalado, não `native-stack`) — é usado uniformemente em telas de qualquer profundidade de aninhamento (ex.: `User.tsx`, dentro do tab navigator, navegando para `"Login"` no stack raiz); isso funciona porque uma `navigate()` para uma rota que o navigator mais próximo não conhece sobe (bubble) para o navigator pai até achar — comportamento documentado do React Navigation, não um hack. Ao adicionar uma nova tela/rota com parâmetros, adicione a entrada em `RootStackParamList`/`MainTabParamList` em vez de usar cast manual em `useRoute()`.

## Estado e persistência

- **zustand**: cada store em `src/stores` é um `create()` simples, sem middleware de persistência. Exemplos: `UserStore` guarda o perfil do usuário logado em memória, `AuthStore` guarda `isLoggedIn` e `sessionExpired` (sessão — deliberadamente separado de `UserStore`, que é perfil/exibição; é a única fonte de "logado" que reage a login/logout **depois** do boot — ver "Autenticação e sincronização"), `ThemeStore`/`FontSizeStore`/`LanguageStore` guardam a preferência atual em memória, `AlertStore` controla um alerta global (`ThemedAlert`, renderizado uma vez em `App.tsx`).
- **Persistência real** é feita diretamente via `AsyncStorage` nos hooks/telas que precisam, usando chaves fixas já estabelecidas: `"User"` (legado, ainda escrito por `EditProfile.tsx`), `"CachedProfile"` (só diz QUEM é a conta logada — o `remoteId` —; XP e Bits vêm do SQLite, que muda a cada lição e que o JSON nunca acompanharia — ver "XP, níveis e Bits"; escrito por `AuthService` após login/registro, lido por `getCachedProfile` no boot), `"Classes"`, `"CurrentTheme"`, `"CurrentLanguage"`, `"CurrentFontSize"`, `"ContentVersions"` (JSON por idioma com `syncedId`/`seenId` e as notas do aviso pendente — ver "Aviso de conteúdo atualizado"), `"NotificationsEnabled"` (`"true"`/`"false"`; ausente = a pessoa ainda não decidiu). Os hooks `useCustomTheme`, `useLanguage`, `useFontSize` e `useAuthSession` leem essas chaves na montagem e são usados em `App.tsx` para popular as stores antes de esconder a splash screen. Ao adicionar uma nova preferência persistida, siga esse mesmo padrão (chave fixa em `AsyncStorage` + hook de leitura + store zustand) em vez de introduzir uma nova abordagem de persistência.
- **Tokens de sessão** (`refreshToken`, `accessToken`, `accessTokenExpiresAt`) ficam em `expo-secure-store` (`src/services/SecureTokenStore.ts`), nunca em AsyncStorage — "logado" é definido só pela presença do refresh token ali, nunca por uma chamada de rede ter sucesso (ver seção "Autenticação e sincronização").
- **A conexão do SQLite é única, no escopo do módulo** (`const database = SQLite.openDatabaseSync("Users.db")` no topo de `DatabaseClient.ts`), compartilhada por todas as instâncias, e **não existe `close()`**. O `expo-sqlite` faz pooling por nome de banco: abrir `"Users.db"` de novo devolve *a mesma* conexão. Enquanto cada `new DatabaseClient()` abria a sua e alguns call sites chamavam `close()` num `finally`, a classe parecia dona de uma conexão que era compartilhada — o `close()` do login derrubava o banco para todo mundo, e a primeira conclusão de lição depois disso estourava com `NullPointerException` no `execSync`. Não reintroduza um `close()` por instância.
- **IDs de evento de sync são UUID** (`randomUUID()` do `expo-crypto`), não `nanoid`. O `clientEventId` viaja para `POST /sync`, cujo schema exige `format: 'uuid'` — um id do nanoid é rejeitado com 400. O `nanoid` padrão ainda dependia de `crypto.getRandomValues`, que não existe no runtime do React Native sem polyfill.
- **Dívida conhecida na fila de sync**: um evento malformado bloqueia a fila inteira. O `/sync` valida o lote todo, então um único evento inválido devolve 400 e `flushQueue` reverte *todos* para `pending`, repetindo para sempre. A causa conhecida (nanoid vs uuid) foi eliminada, mas o `SyncService` continua tratando 400 (validação) igual a falha de rede; se isso voltar a morder, o caminho é marcar como `failed` em vez de `pending` nesse caso.
- **`DatabaseClient`** (`src/services/DatabaseClient.ts`) encapsula o SQLite local (`expo-sqlite`, banco `Users.db`) com tabelas `Users`, `UserLessons`, `SyncQueue` e `UserAchievements`; é instanciado diretamente nas telas/serviços que precisam (ex.: `AuthService`), não é injetado via store/contexto. `initDefaultTables()` cria as tabelas base e chama `runMigrations()` (`src/services/migrations.ts`, guiado por `PRAGMA user_version`) para aplicar alterações de schema que `CREATE TABLE IF NOT EXISTS` não cobre (novas colunas/tabelas). Ao precisar de uma nova alteração de schema local, adicione um novo `if (version < N)` em `migrations.ts` em vez de editar o SQL de uma versão já aplicada — **exceto** enquanto o app não tiver sido rodado/distribuído com aquela versão em nenhum dispositivo real (nosso caso até agora): nesse cenário é seguro e preferível editar a migração já numerada em vez de acumular versões que nunca chegaram a aplicar de fato. Assim que o app rodar de verdade com uma versão aplicada, essa versão passa a ser imutável.
- **Sem autenticação local**: como o registro de conta exige internet (sempre via `/auth/register`), o modelo antigo de login 100% local (senha em texto puro em `Users.password`, comparada com `===`) foi removido — `DatabaseClient` não tem mais `registerUser`/`validateUser`/`updateUserPassword`. `ChangePassword.tsx` abre o fluxo de troca de senha por e-mail — ver "Confirmação de e-mail, troca e recuperação de senha".
- **`Users.remoteId` é a própria chave primária local** (`TEXT PRIMARY KEY`, o `users.id`/UUID retornado pela API) — não existe mais um `id INTEGER` autoincrement separado. Isso só foi possível porque `remoteId` deixou de ser opcional: toda linha nasce de `DatabaseClient.upsertLocalProfile()`, que sempre recebe o `remoteId` vindo da API, então não há mais motivo para uma chave substituta local. `UserLessons.userId` é `TEXT`, referenciando `Users.remoteId` diretamente (antes era `INTEGER` → `Users.id`; `UserLessons.id` continua um `INTEGER AUTOINCREMENT` normal — é só a PK da própria linha de conclusão, igual `user_lessons.id` no Postgres, nunca o ID da lição em si, que já é `lessonId`).
- **`Aulas`/`TipoAula` viraram `UserLessons`/`lessonId`** (tabela e coluna) — nome antigo era a única tabela em português no schema local (todo o resto já era inglês) e não deixava claro que se trata do relacionamento N:N usuário↔lição, igual `UserAchievements`; o novo nome bate com o model equivalente da API (`user_lessons`). **Cuidado para não confundir com a chave AsyncStorage `"Aulas"`** (usada por `Html.tsx`/`Css.tsx`/`Js.tsx` em `screens/classes/lessons/`) — é um mecanismo completamente separado, não relacionado ao SQLite, e não foi tocado por esse rename.
- **Todas as colunas locais são camelCase** (`id`, `userId`, `remoteId`, `lessonId`, `achievementId`, `clientEventId`...) — segue o mesmo critério que a própria API já usa em `api/src/types/contracts.ts`: `snake_case` só onde o tipo é derivado direto de uma linha do Prisma/Postgres (`UserResponse = Omit<users, 'password'>`, ex. `created_at`), `camelCase` em tudo que é um formato só de TypeScript (`SyncEventInput.payload.lessonId`/`achievementId`, `accessToken`, etc.). O SQLite local não é um espelho do Postgres — tem seu próprio formato —, então segue a mesma regra dos DTOs, não a das tabelas do Postgres. Nomes de tabela continuam PascalCase (`Users`, `UserLessons`, `SyncQueue`, `UserAchievements`) — é só convenção de identificador, sem relação com essa regra de coluna.
- **O dispositivo pode ter mais de uma conta ao longo do tempo** (logout/login de outro usuário no mesmo aparelho) — por isso `UserAchievements` e `SyncQueue` também carregam `userId` (`TEXT`, FK para `Users.remoteId`), não só `UserLessons`. Sem isso, uma conquista ou um evento pendente de um usuário podia vazar ou ser sincronizado sob a sessão de outro. `UserAchievements.UNIQUE` passou de "achievementId global" para `(userId, achievementId)` — cada usuário pode desbloquear a mesma conquista independentemente.
  Esquema local hoje (`Users.db`, versão 6 — `migrations.ts`):
  - `Users(remoteId TEXT PK, name, email, bits, xp, doubleXp, doubleTime, doubleXpEndsAt, lastProfileSyncAt)` — `doubleXp`/`doubleTime` são colunas legadas, nunca lidas; `doubleXpEndsAt` (TEXT ISO, v6) é o fim da janela de Dobro de XP que o servidor concedeu
  - `UserLessons(id INTEGER PK AUTOINCREMENT, userId TEXT FK→Users.remoteId, lessonId)`
  - `SyncQueue(id INTEGER PK AUTOINCREMENT, userId TEXT FK→Users.remoteId, clientEventId TEXT UNIQUE, type, payload, occurredAt, status, attempts, lastError, createdAt, updatedAt)`
  - `UserAchievements(id INTEGER PK AUTOINCREMENT, userId TEXT FK→Users.remoteId, achievementId, unlockedAt, UNIQUE(userId, achievementId))`
  A migração de versão 3 reconstrói `Users`/`UserLessons` (SQLite não permite trocar a PK de uma tabela existente via `ALTER TABLE`) e descarta, nesse processo, qualquer linha local sem `remoteId` (resíduo do cadastro 100% local antigo, hoje impossível de recriar) e as aulas associadas a ela. A versão 4 reconstrói `UserAchievements` (pela troca da constraint única) e adiciona `userId` em `SyncQueue`; em ambos os casos, linhas pré-existentes sem forma confiável de atribuir um usuário são descartadas/marcadas `failed` — na prática não havia dado real perdido, já que na época nenhuma tela chamava os métodos que escrevem nessas tabelas. A versão 6 só adiciona `Users.doubleXpEndsAt` — **conferindo antes se a coluna já existe** (`PRAGMA table_info`): um banco que ganhou a coluna sem registrar a versão (visto no emulador, depois de builds intermediários) repetia o `ALTER` e o login quebrava com `duplicate column name`. Migração nova que adiciona coluna deve ser idempotente do mesmo jeito: offline-first não pode travar o app numa migração. A versão 5 renomeia `Users.dependaBots` para `bits` (`ALTER TABLE … RENAME COLUMN`, preserva os valores); o `CREATE TABLE` base de `initDefaultTables` e a migração 3 continuam falando `dependaBots`, porque são histórico já aplicado — o renome vem por último.

## Autenticação e sincronização

- **Fluxo de login**: `Login.tsx` chama `useLoginMutation` (React Query, `src/hooks/queries/`), que chama `AuthService.login` (`src/services/AuthService.ts`). Sucesso: `SecureTokenStore.saveSession` (tokens) + `DatabaseClient.upsertLocalProfile` (cache local do perfil, por `remoteId`) + `AsyncStorage["CachedProfile"]`, retornando um `User` (formato local) já pronto para `setUser()`.
- **Fluxo de registro — deliberadamente NÃO faz login automático**: `AuthService.register` chama `/auth/register` (que emite uma sessão, útil para outros clientes), mas revoga esse refresh token em seguida via `/auth/logout` (best effort) em vez de persistir sessão — o app quer que o usuário passe pela tela de Login para escolher "lembrar-me" explicitamente. `Register.tsx` mostra o alerta de sucesso e, ao ser dispensado, navega para `"Login"` passando `{ email }` como route param; `Login.tsx` lê isso via `useRoute()` num `useEffect` (não como valor inicial do `useState`, porque a tela de Login normalmente já está montada na pilha por baixo de Register, então o valor inicial não seria reavaliado) e pré-preenche o campo de e-mail.
- **"Logado" nunca depende de rede**: `useAuthSession` (`src/hooks/useAuthSession.ts`) só verifica se existe um refresh token no `SecureTokenStore` — é isso que `App.tsx` usa para decidir `isLoggedIn` antes de esconder a splash screen, e `MainNavigation.tsx` usa para escolher `initialRouteName` ("Home" ou "Login") sem nunca montar a tela de Login para quem já está logado.
- **`MainNavigation` recebe `isLoggedIn` como prop, não lê da `AuthStore`** — de propósito. `App.tsx` só monta `<NavigationContainer>`/`<MainNavigation>` depois que `useAuthSession()` já resolveu (`isReady`, ver `App.tsx`); antes disso retorna `null` (a splash nativa cobre essa espera). Isso existe porque `Stack.Navigator` só lê `initialRouteName` uma vez, no primeiro mount, e não reage a mudanças depois — se `MainNavigation` montasse cedo demais lendo `AuthStore.isLoggedIn` (cujo valor inicial é `false`), a rota inicial travaria em `"Login"` mesmo com uma sessão válida no `SecureStore`, e só apareceria de novo depois de um logout/login manual. Não reverta para `MainNavigation` ler direto da store sem resolver essa ordenação.
- **Deep linking (`App.tsx`, prop `linking` do `NavigationContainer`) usa a `AuthStore`, não o `isLoggedIn` local** — motivo oposto ao do ponto acima. A config de `linking` (`useMemo`) só inclui as rotas de `Home` quando logado, pra um deep link não conseguir entrar numa tela protegida estando deslogado; mas diferente do `initialRouteName`, essa config **precisa** reagir durante a sessão (ex.: logout em runtime, feito por `User.tsx` via `clearSession()`). Como `isLoggedIn` (de `useAuthSession()`) é congelado no boot por design, ele nunca refletiria esse logout — daí `linking` usar `useAuthStore((s) => s.isLoggedIn)` em vez disso. Pra essa store já nascer com o valor certo (e não com o default `false`) antes do primeiro deep link de cold start ser resolvido, `useAuthSession()` chama `setSession()` da própria `AuthStore` dentro do mesmo `hydrate()` que resolve `isLoggedIn` — não num efeito separado em `App.tsx`, que rodaria tarde demais (depois do efeito de mount do `NavigationContainer`, que é filho). Ao adicionar uma nova tela protegida ao mapa de `linking.config.screens`, garanta que ela só entra no ramo `authIsLoggedIn` verdadeiro.
- **Renovação de access token**: `ApiClient.ts` (axios) intercepta toda requisição fora de `/auth/*` — mais as rotas de conta logada de `AUTHENTICATED_AUTH_ROUTES` (ver "Confirmação de e-mail…") — e chama `ensureFreshAccessToken()` antes de anexar o `Authorization: Bearer`; se o token está perto de expirar, renova via `/auth/refresh` (essa chamada em si é pulada pelo interceptor, evitando recursão). Falha de rede aqui nunca lança — segue com o token em cache (mesmo vencido) para a chamada falhar naturalmente offline, em vez de bloquear o app.
- **`ensureFreshAccessToken()` roda uma execução por vez** (promise compartilhada em `ApiClient.ts`). No boot, a hidratação da sessão, o flush da `SyncQueue` e as queries de conteúdo chamam a função quase juntas; sem isso, cada uma leria o mesmo refresh token e chamaria `/auth/refresh`, e a API trata a segunda como **reuso** — revoga a família inteira e o usuário é deslogado sem ter feito nada. A promise compartilhada cobre a função inteira (inclusive a leitura do SecureStore), não só a chamada de rede, para a próxima execução só ler depois que a anterior salvou o par novo. Não troque por uma deduplicação só em volta do `apiClient.post("/auth/refresh")`.
- **`/auth/refresh` tem timeout próprio de 15 s** (`REFRESH_REQUEST_TIMEOUT_MS` em `ApiClient.ts`; o `apiClient` em si não tem nenhum). Como toda requisição autenticada espera essa renovação, sem teto uma rede que conecta e não responde deixaria a sincronização pendurada por minutos. Estourar o teto conta como falta de rede: segue com o token em cache, sem deslogar. **Não encurte para algo como os 4 s do `ContentVersionService`**: se a API concluir a troca depois que o app desistiu, o par novo se perde, o app fica com o refresh token já revogado e a próxima tentativa é tratada como reuso, deslogando o usuário. O teto precisa ficar bem acima do pior caso legítimo da API (inclusive o banco serverless acordando).
- **Sessão expirada (401 no `/auth/refresh`)**: o refresh token foi rejeitado de verdade (revogado, expirado ou reuso), não é falta de rede. `ApiClient.ts` limpa o SecureStore e chama `AuthStore.expireSession()` (`isLoggedIn: false` + `sessionExpired: true`). Um efeito em `App.tsx` reage a esse flag: zera a `UserStore`, faz `reset` da pilha para `"Login"` (via `useNavigationContainerRef`) e mostra o `ThemedAlert` global com `login.alert.sessionExpired`. O efeito espera o `onReady` do `NavigationContainer`, porque o 401 pode chegar durante o boot, antes da navegação existir; o flag fica de pé até ser tratado. O logout manual (`User.tsx`) usa `clearSession()`, não `expireSession()`, e por isso não mostra o aviso.
- **Fila de sincronização offline-first**: `DatabaseClient.completeLesson(userId, lessonId)` e `.unlockAchievement(userId, achievementId)` gravam o dado de domínio (`UserLessons`/`UserAchievements`) e um evento em `SyncQueue` (com o mesmo `userId`) na **mesma transação** (`withTransactionSync`) — é essa atomicidade que garante que progresso e pendência de sync nunca divirjam. `SyncService.flushQueue()` (`src/services/SyncService.ts`) resolve o usuário atual via `AuthService.getCachedProfile()` e só lê/envia os eventos `pending` **daquele usuário** (`getPendingSyncEvents(userId)`) — pendências de uma conta que não está logada no momento ficam intocadas, nunca enviadas sob a sessão errada. Marca `syncing`, envia em lote para `POST /sync`, atualiza para `synced`/`failed` conforme a resposta por evento; falha de rede/transporte devolve tudo para `pending` (nunca marca `failed`) para tentar de novo depois. Protegido por um lock em memória (`isFlushing`) contra chamadas concorrentes. Se não há perfil em cache (ninguém logado), o flush não faz nada.
- **Gatilhos de sync**: `useNetworkSync` (chamado uma vez em `App.tsx`) dispara no boot e na transição offline→online (`@react-native-community/netinfo`); `useLoginMutation` dispara logo após um login bem-sucedido (drena qualquer fila que já existisse localmente para aquela conta, já que `useNetworkSync` não roda de novo a cada login dentro do app já aberto); `SyncService.recordLessonCompletion(userId, lessonId, xpReward?)`/`recordAchievementUnlock(userId, achievementId)` gravam localmente e já chamam `flushQueue()` em seguida (fire-and-forget) — use essas duas funções em vez de `DatabaseClient.completeLesson`/`unlockAchievement` diretamente quando for plugar isso numa tela, para não perder esse gatilho. **Quem chama hoje**: `Lesson.tsx` (`recordLessonCompletion`, que devolve o `LessonCompletionResult` para a tela de conclusão, ao terminar a última atividade) e o `AchievementService` (`recordAchievementUnlock`, ver "Conquistas").
- **Tipos compartilhados**: `AuthResponse`, `LoginBody`, `RegisterBody`, `SyncEventInput`, etc. vêm de `codap-api/src/types/contracts` (`import type` — apagado no build, sem custo no bundle). Reaproveite esses tipos em vez de redeclarar os formatos de request/response da API.
- **Variável de ambiente**: `EXPO_PUBLIC_API_URL` (ver `.env`/`.env.example`) define a base URL da API consumida por `ApiClient.ts`. **`localhost` não funciona a partir de um emulador/dispositivo** (resolve para o próprio emulador/dispositivo, não para a máquina rodando a API) — use `http://10.0.2.2:3000` no emulador Android (alias especial para o `127.0.0.1` do host), `http://localhost:3000` no simulador iOS (compartilha a rede do host), ou o IP da máquina na LAN para um dispositivo físico.

**Cuidado com `TouchableWithoutFeedback` do `react-native-gesture-handler`**: a versão do gesture-handler tem um bug conhecido no Android onde toques não chegam a um `Switch` nativo aninhado dentro dela (o toggle "lembrar-me" do login). Por isso `AuthLayout` (casca do login e do cadastro) não usa `TouchableWithoutFeedback` nenhum: dispensa o teclado ao rolar (`onScrollBeginDrag`) e deixa os toques passarem (`keyboardShouldPersistTaps="handled"`). Não envolva o formulário numa dessas áreas de toque sem verificar se ainda há um `Switch` dentro.

## Confirmação de e-mail, troca e recuperação de senha

O lado do servidor (regras, rotas, tokens) está em [api/CLAUDE.md](../api/CLAUDE.md), "E-mails de conta". **A regra que orienta o app: senha só com o e-mail confirmado**, porque um endereço digitado errado pode ser de um estranho. Tudo abaixo é a interface dessa regra.

- **Quem sabe se está confirmado é o servidor, e o app nunca grava isso.** `EmailStatusStore` (zustand, só memória) guarda `email`, `verified` (`null` = ainda não se sabe) e o estado do modal; `refreshEmailStatus()` (`hooks/useEmailStatus.ts`) chama `GET /auth/me` (`AccountService.fetchAccountEmail`). Sem rede, nada acontece: o aviso só aparece com a resposta do servidor, nunca por um dado antigo do aparelho. A confirmação acontece **no navegador**, fora do app, então ele pergunta de novo ao entrar, **quando volta ao primeiro plano** (`AppState`) e ao focar o Perfil.
- **Aviso na abertura** (`components/EmailVerification.tsx`, montado dentro do `Provider` em `App.tsx`; usa `Portal`): na primeira resposta "não confirmado" da sessão abre o `EmailVerificationModal`. `autoPrompted` (memória) impede que voltar ao primeiro plano abra de novo; fechar o app e abrir outra vez — ou entrar de novo — mostra de novo, como combinado com o desenvolvedor. Fechar nunca é um beco sem saída: a linha **"Confirmar e-mail"** do Perfil (`ConfirmEmail.tsx`, só enquanto `verified === false`, com o selo âmbar "Pendente") reabre. Abrir o modal **não manda e-mail**: o de confirmação já saiu no cadastro; só o botão "Reenviar" manda.
- **`EmailVerificationModal`** (`AppModal`, um só para o app inteiro, aberto pela store com um motivo: `prompt` ou `passwordChange`): estado **info** (o endereço numa placa, `EmailAddress`; "Reenviar e-mail" com contagem de 60 s — `useCooldown`, o limite do servidor — e "Corrigir e-mail"), estado **fix** (campo para o endereço certo; `POST /auth/change-email` só funciona enquanto o e-mail não está confirmado, que é o caso do erro de digitação; se o servidor sugere uma correção de domínio, aparece "Usar fulano@gmail.com") e estado **confirmado** (quando a confirmação chega com o modal aberto). Corrigir atualiza o e-mail na store, na `UserStore` e no SQLite (`DatabaseClient.setLocalEmail`).
- **Alterar senha** (`ChangePassword.tsx`): sem e-mail confirmado abre a confirmação (motivo `passwordChange`); se o app ainda não sabe (sem rede desde que entrou), pede ao servidor, que decide — um 403 leva à mesma confirmação. Com e-mail confirmado, o modal mostra **para onde o link vai** e avisa que a pessoa será **desconectada de todos os aparelhos** ao salvar a senha nova (`POST /auth/request-password-change`). A senha nova é criada numa página da API aberta pelo link do e-mail, no navegador; ao salvar, a sessão do app cai e ele segue o fluxo de "sessão expirada" que já existe.
- **"Esqueci minha senha"** (`Login.tsx` → `ForgotPasswordModal`): link logo abaixo do campo de senha. A resposta do servidor é sempre a mesma, exista a conta e esteja o e-mail confirmado ou não, então a tela também só diz "se estiver cadastrado e confirmado, o link está a caminho" — e diz a regra antes de enviar. O e-mail digitado no login vem preenchido.
- **Erros** (`AccountService.classifyAccountError` → `utils/accountErrorText.ts`): o servidor decide a **causa** (status e `code`) e o texto vive no i18n (`accountErrors.*`), então sai no idioma da pessoa. `email_typo` (400, domínio com cara de erro — `gmial.com`, só em produção) traz a `suggestion`; o cadastro (`Register.tsx`) e o modal de correção a usam. Chaves: `emailStatus.*`, `passwordChange.*`, `forgotPassword.*`, `accountErrors.*`, `register.alert.typo.*`.
- **`ApiClient`**: o interceptor só pula o Bearer nas rotas de `/auth/*` que **não** são de conta logada; `/auth/me`, `/auth/resend-verification`, `/auth/request-password-change` e `/auth/change-email` estão em `AUTHENTICATED_AUTH_ROUTES` e levam o token. **Rota nova de conta logada sob `/auth/` precisa entrar nessa lista**, senão a chamada chega sem Bearer e falha com 401 sem nenhum erro óbvio.
- **Conta de teste `teste@teste.com`** (só em desenvolvimento): conta como e-mail confirmado, então o aviso nunca aparece para ela; o link de redefinição dela vai para o **log da API** em vez de um e-mail.
- **Peças visuais compartilhadas**: `EmailAddress` (o endereço como dado em destaque, placa rebaixada `colors.card`) e `StatusLine` (resultado de uma ação: ícone + texto verde ou vermelho — o ícone repete o que a cor diz, e a região é anunciada pelo leitor de tela). Os modais são `AppModal`s com `AppButton`s (primária e secundária), como os demais; a cor de atenção do selo "Pendente" é a âmbar da paleta (`warning`), não o vermelho de erro.

## Conquistas

Quatro emblemas, numa grade 2×2 aberta pelo botão "Conquistas" do Perfil (`screens/user/components/achievements/`): **HTML**, **CSS** e **JavaScript** (concluir todas as lições da área) e **Tríade Web** (ter os três emblemas — o básico do desenvolvimento web). Ordem da grade em `achievementCatalog.ts`: a trilha na ordem ensinada e a Tríade por último. Imagens `assets/emblema_*.png` (fundo transparente, registradas em `imageIndexer.ts`).

- **Ids fixos, não autoincrement**: `ACHIEVEMENT_IDS` (`services/AchievementService.ts`) = `html: 1, css: 2, javascript: 3, webTriad: 4`, os mesmos de `ACHIEVEMENTS` em `api/prisma/seed.ts`. A conquista é decidida aqui, offline, e viaja para `/sync` só pelo id — os dois lados precisam concordar sem consulta. Mudou um, mude o outro. A conquista de cada área é achada pela **posição** em `GET /areas` (0 = HTML…), mesma regra de `areaMetadata.ts`.
- **Nenhuma requisição para ler o status.** Uma conquista obtida nunca volta atrás, e quem decide o desbloqueio é o app: o SQLite (`UserAchievements`) é a fonte da verdade, e a nuvem só *recebe* cada desbloqueio uma vez, pela fila de sync (`recordAchievementUnlock` → `achievement_unlocked`). Por cima do SQLite fica a **`AchievementStore`** (zustand, memória), carregada **uma vez por usuário e por sessão** (`loadAchievements`, no-op nas chamadas seguintes; trocar de conta recarrega, porque a store guarda o `userId` dono). A "invalidação" é o próprio desbloqueio: grava no SQLite + enfileira o sync + `markUnlocked` na store, e a tela re-renderiza.
- **Quando confere**: `Lesson.tsx` chama `evaluateAfterLesson(remoteId, areaId)` logo depois de `recordLessonCompletion` — o único momento em que o status pode mudar — e só confere a área daquela lição, mais a Tríade. A primeira carga da store (`loadAchievements`, ao abrir a grade ou na primeira lição concluída da sessão) faz uma conferência completa, **retroativa**, para quem já tinha concluído uma área antes das conquistas existirem. Tudo síncrono: o evento da conquista entra na fila no mesmo tick do da lição e os dois vão para `/sync` no mesmo lote.
- **"Área concluída"** (`isAreaComplete`, função pura): todas as lições da área com ao menos uma atividade que o app sabe reproduzir (`filterPlayable`) estão em `UserLessons`. **Aulas de aprofundamento (com `minLevel`) são opcionais e ficam de fora dessa conta** (`isOptionalLesson`): nunca impedem o emblema. Lição sem nenhuma atividade suportada (abre o "em breve") não conta — não teria como ser concluída nesta versão. Área sem nenhuma lição exigida nunca conta como concluída. O catálogo vem do **cache** do React Query (`["modules", areaId, <idioma>]`, de preferência no idioma atual; qualquer idioma serve, ids de lição não mudam com a tradução) — sem cache, a área nunca foi aberta no dispositivo e não pode ter sido concluída nele. Nada aqui dispara rede.
- **Não obtida = encaixe vazio** (`AchievementEmblem.tsx`): a silhueta sai da própria imagem via `tintColor`, em três camadas — luz deslocada para baixo, sombra para cima e o preenchimento mais escuro que o cartão por cima —, um baixo-relevo sem precisar de um segundo arquivo por emblema. Cores por tema em `HOLE_COLORS`. Resíduos do removedor de fundo nas imagens aparecem nitidamente na silhueta (o de JavaScript, sobretudo).
- **Toques**: toque rápido numa **obtida** abre a `AchievementSpotlight` (Modal do RN, fundo quase preto, emblema grande com brilho radial em `react-native-svg` pulsando — o pulso é desligado com "reduzir movimento"); qualquer toque nela, dentro ou fora do emblema, ou o voltar do Android, fecha. Toque rápido numa **bloqueada** não faz nada, de propósito (nem em dev).
- **Só em dev (`__DEV__`)**: segurar um emblema por 5 s inverte como ele aparece, para ver o visual sem mexer no banco. O override vive só no estado do `AchievementsModal` — nunca toca no SQLite, na fila nem na store —, mostra um selo "DEV" e some ao voltar ao estado real. Em produção o `onLongPress` nem é passado.
- **Limitação conhecida**: não existe *pull* do progresso. Num dispositivo novo (ou depois de reinstalar), `UserAchievements` começa vazio — o mesmo que já acontece com `UserLessons`. O servidor tem os dados (`user_achievements`), mas nenhum endpoint os devolve ao app ainda.
- Chaves i18n em `achievement.*` (`<key>.name`/`hint`/`description`, `close`, `locked`, `tapToClose`).

## XP, níveis e Bits

Desenho completo em [docs/superpowers/specs/2026-10-18-xp-niveis-bits-design.md](../docs/superpowers/specs/2026-10-18-xp-niveis-bits-design.md). A Fase 1 (esta) cobre nível, XP local, tela de conclusão e a troca de "Dependabots" por **Bits**; a loja funcional e o baú vieram depois — ver "Loja e baú" abaixo — e as aulas opcionais por nível, em "Aulas de aprofundamento".

- **Nível derivado do XP** (`src/utils/levels.ts`, funções puras): de 1 a 50, `threshold(n) = round(0,41·(n−1)² + 54·(n−1))` — nível 2 = 54 XP, 10 = 519, 19 = 1105, 30 = 1911, 50 = 3630. Com 10 XP por lição, a trilha de HTML fecha no nível 10, HTML + CSS no 19 e a trilha toda no 30; os níveis 31 a 50 só se alcançam com conteúdo opcional futuro. **Duplicado em `api/src/utils/levels.ts`** (o app importa `codap-api` só como tipo, então não dá para compartilhar código executável): mudou um, mude o outro. **Bits:** `10 × n` ao alcançar o nível `n` (n ≥ 2), só ao cruzar o nível.
- **XP e Bits locais (offline-first)**: `DatabaseClient.completeLesson` soma o XP e os Bits dos níveis cruzados em `Users.xp`/`Users.bits` **na mesma transação** que grava `UserLessons` e o evento da fila, e devolve um `LessonCompletionResult` (`firstTime`, `xpGained`, `bitsGained`, `xpBefore/After`, `levelBefore/After`, `bitsAfter`). **Só a primeira conclusão de cada lição rende**: se a lição já está em `UserLessons`, não grava nada e devolve `firstTime: false` — o servidor também a trataria como duplicada, e sem essa regra o XP local passaria do dele. `SyncService.recordLessonCompletion` repassa o resultado e atualiza a `UserStore`.
- **O servidor é a autoridade, e o app se corrige.** O número local é uma estimativa imediata (para o nível reagir sem rede). `POST /sync` devolve `profile: { xp, bits }`, e `flushQueue` adota esses valores quando, **depois da resposta**, o usuário não tem mais eventos `pending`/`syncing` (`hasUnsyncedEvents`; `failed` é terminal e não impede). A checagem vem depois da resposta porque uma lição concluída durante a requisição entrou na fila e o servidor ainda não a conhece, e a adoção fica **fora** do `try` do envio: uma falha nela nunca pode devolver para `pending` eventos já marcados `synced`. **Com a fila vazia o `flushQueue` ainda manda `{ events: [] }`** (com timeout próprio de 8 s: o `apiClient` não tem timeout, e um servidor que não responde seguraria o lock do flush e bloquearia os envios seguintes) — é isso que corrige, no boot, o XP de quem já tinha XP antes de o app calculá-lo localmente (o SQLite guardava o XP do dia do login), e que traz Bits retroativos e progresso de outro dispositivo. E, no início de cada flush, os eventos presos em `syncing` (app encerrado com o envio em voo) voltam para `pending` (`releaseSyncingEvents`): sem isso `hasUnsyncedEvents` ficaria verdadeiro para sempre e a autocorreção se desligaria. **Ordem de publicação:** o renome da coluna no Postgres quebra uma API antiga (o Prisma seleciona `dependabots`), então a migration e o código novo da API têm de ir juntos; contra uma API antiga, o app novo grava `bits = 0` no login quando a fila está vazia (`authResponse.user.bits` vem indefinido), o que se corrige quando a API nova responde. No login, `upsertLocalProfile` segue a mesma regra (fila vazia → vale o servidor; com pendentes → `max(local, servidor)`, para um login não apagar o que ainda vai ser enviado). Isso cobre reinstalação, outro dispositivo e uma lição removida do catálogo. **Limitação conhecida:** refazer uma lição já concluída num aparelho sem o histórico (`UserLessons` vazio) mostra "+10 XP" na tela de conclusão por um instante, e o valor volta ao correto quando a sincronização termina — só um *pull* do progresso, que não existe, evitaria isso.
- **`getCachedProfile` lê o SQLite**: o JSON do AsyncStorage (`"CachedProfile"`) só diz quem é a conta (`remoteId`); devolvê-lo como está mostraria o XP do dia do login. O campo legado `dependaBots` desse JSON é ignorado.
- **Tela de conclusão** (`LessonComplete`): ao terminar a última atividade, `Lesson.tsx` não volta direto — guarda o resultado e mostra "+10 XP", a barra (`LevelBar`, componente reutilizado pelo perfil) animando do progresso anterior ao novo e, numa subida de nível, "Nível N!" com os Bits ganhos; a barra enche, recomeça e segue até o novo valor. Com "reduzir movimento" ligado mostra direto o estado final. Refazer uma lição mostra "você já tinha concluído esta lição" e nada mais. A ordem em `finish` se mantém: `recordLessonCompletion` → `evaluateAfterLesson` (conquistas) → tela de conclusão.
- **Perfil**: o `UserHeader` mostra o título, os Bits (no canto, como no Mercado) e, logo abaixo, "Nível N", "atual / necessário XP" (ou "Nível máximo") e a barra até o próximo nível (`LevelBar`). O antigo cartão `LevelProgress` saiu da rolagem; o XP total deixou de aparecer. **Nível e XP não aparecem nas trilhas**, por decisão do desenvolvedor (pode mudar no futuro). A tela é um cartão de identidade (avatar, nome e e-mail) seguido de `ListRow`s: Editar perfil, Alterar senha, Conquistas e Sair (em vermelho). O avatar e os rótulos acompanham o tema; nome e e-mail usam `colors.text`.
- **Aulas de aprofundamento** ([spec](../docs/superpowers/specs/2026-10-18-aulas-aprofundamento-design.md)): uma lição com `minLevel` é opcional, abre a partir desse nível (`levelForXp` do XP local, então funciona offline e reage na hora) e paga o XP dela (`xpReward`, padrão 10). As três regras vivem em `utils/lessonAccess.ts` (funções puras: `isOptionalLesson`, `isLessonUnlocked`, `lessonXpReward`), e **uma lição sem `minLevel` — inclusive um cache antigo do catálogo, que ainda não traz o campo — é da trilha principal**; por isso o `persistOptions.buster` não foi bumpado (um cache antigo significa "sem aulas opcionais", que é o resultado certo até a `content_version` seguinte recarregar o catálogo). Na lista (`AreaModules` → `ClassButton`): liberada ganha borda roxa sutil (`#8E7CC3`) e um foguete, menos chamativa que o troféu dourado do desafio do módulo; bloqueada fica apagada, com borda tracejada, cadeado e "Nível N", e **não responde ao toque**. `Lesson.tsx` barra uma aula bloqueada aberta à força (deep link) com `LessonLocked` e não roda nem paga nada; ao concluir, passa `lessonXpReward(lesson)` para `recordLessonCompletion`/`completeLesson(userId, lessonId, xpReward)`, e a tela de conclusão já mostra o ganho real (o nível pode subir mais de uma vez com um XP alto, e os Bits de todos os níveis cruzados são pagos). **`isAreaComplete` ignora aulas opcionais**: uma aula de aprofundamento nunca impede o emblema da área. O servidor lê o mesmo XP de `lessons.xp_reward`, então o app e o `/sync` concordam sem consulta; se divergirem, a adoção do `profile` corrige. As aulas exclusivas do baú são outra coisa — ver "Loja e baú".
- **Bits na interface**: ícone `octicons`/`cpu` (o antigo `dependabot` era a marca da GitHub) em `MarketHeader`, `MarketModal` e nos três cartões da loja. Os preços (Dobro de XP 200, Dica Instantânea 300, Baú Surpresa 500) vêm de `GET /shop`; `FALLBACK_PRICES` em `Market.tsx` só preenche a tela enquanto o estado não chegou, e sem o estado a compra nem é oferecida.
- **Como verificar sem emulador**: o app não tem suíte de testes. A lógica de SQLite, migrações e sync (`DatabaseClient`, `migrations.ts`, `SyncService`, `getCachedProfile`) foi exercitada com um harness descartável: `node:sqlite` em memória no lugar do `expo-sqlite` e mocks de `expo-crypto`, AsyncStorage e `ApiClient`, rodado com o `tsx` da API. O `tsx` compila o app como CommonJS (sem `"type": "module"` no `package.json`), então os mocks entram por um patch em `Module._load` — `Module._resolveFilename` não alcança imports relativos de `.ts` como `./ApiClient`, e um `register` de hooks ESM não alcança `require`. A interface (animação, perfil) só foi checada por tipo; a conferência visual no emulador continua pendente.

## Loja e baú

Desenho em [docs/superpowers/specs/2026-10-19-loja-e-bau-design.md](../docs/superpowers/specs/2026-10-19-loja-e-bau-design.md); o lado do servidor está em [api/CLAUDE.md](../api/CLAUDE.md), "Loja e baú". Três itens, todos pagos em Bits: **Dobro de XP** (200, janela de 5 minutos), **Dica Instantânea** (300, vai para o estoque) e **Baú Surpresa** (500).

- **Comprar exige internet, de propósito.** Quem decide o saldo é o servidor; um log de compras offline obrigaria a desfazer compras. `ShopActions.buyItem(item, language?)` primeiro **envia a fila de sync** (`flushQueue`) e **recusa a compra** (`pending_sync`) se ainda sobrar evento pendente — os Bits de lições feitas offline só existem para o servidor depois disso, e uma recusa por "saldo insuficiente" com o saldo local cobrindo seria incompreensível. Depois chama `POST /shop/purchase` e adota o que voltou: saldo no SQLite (`setLocalBits`) e na `UserStore`, janela do dobro (`setDoubleXpEndsAt`), `ShopStore.patch`. Erros viram um resultado tipado (`offline`, `pending_sync`, `insufficient_bits` com o saldo do servidor, `boost_active`, `error`), e `Market.tsx` os traduz em alertas (`shop.errors.*`). Sem o estado da loja carregado (sem conexão), a compra nem é oferecida.
- **`ShopStore`** (zustand, memória) guarda o estado devolvido por `GET /shop` **junto do `userId` dono**: outra conta no mesmo aparelho nunca o herda (`Market` e o desafio de código só leem o estado se `userId === remoteId`). `refreshShop()` o recarrega — ao focar a loja e ao abrir o desafio de código — e engole falha de rede (a tela segue com o último estado ou sem ele).
- **Dobro de XP funciona offline depois de comprado.** O servidor dobra no máximo 5 lições por janela (`BOOST_MAX_LESSONS`); o app não conhece o teto e pode mostrar o dobro na 6ª lição da janela, e o valor volta ao do servidor quando o `profile` é adotado. `refreshShop` e a compra gravam o fim da janela em `Users.doubleXpEndsAt`, e `completeLesson` dobra o XP (e os Bits dos níveis cruzados) quando `occurredAt <= doubleXpEndsAt`, devolvendo `boosted` para a tela de conclusão mostrar "XP em dobro!". O servidor confere a janela pela hora do evento (`starts_at <= occurredAt <= ends_at`) e é a autoridade: se divergirem, a adoção do `profile` corrige.
- **Dica Instantânea** (`CodeEditorExercise`, `ChallengeHelp`): o botão "Liberar agora" aparece só com estoque e abre o **próximo passo da ajuda** (as dicas e, por fim, a solução) sem esperar as 2 execuções ou os 90 s. `forced` é um **piso**, não uma soma, e o passo seguinte é calculado a partir do que está liberado **no momento da resposta** (lido de um ref): o passo que o tempo abriria durante o pedido não pode ser "gasto" duas vezes. `spendHint` chama `POST /shop/use-hint`; sem estoque (409) zera o estoque local e avisa.
- **Baú e coleção**: a compra do baú devolve `chest` (aula, dica, dobro ou Bits); `Market` mostra o que veio (`shop.chest.*`) e, no modal de confirmação, **quantas** aulas exclusivas cada área tem e quantas já são da pessoa — nunca quais. As aulas reveladas vêm de **`GET /collection`** por `useCollectionQuery` (chave `["collection", remoteId, idioma]`, `staleTime` infinito, persistida como o catálogo; só habilita com `remoteId`). Uma aula nova na coleção invalida `["collection", remoteId]` (`buyItem`), e `useContentVersionSync` a invalida junto do catálogo quando o idioma publica (`isStaleForLanguage` também casa `entity === "collection"`). O `persistOptions.buster` **não foi bumpado**: a chave é nova, e um cache antigo simplesmente não a tem.
- **Na lista de aulas** (`AreaModules`), as aulas da coleção são encaixadas **no fim do módulo** a que pertencem (`moduleId` da própria aula), como `ClassButton chest`: borda magenta (`#D946A8`) e uma caveira (`skull-outline`) — uma forma, não só a cor, para quem enxerga mal cores —, sempre abertas (já foram reveladas) e marcadas ao concluir. `Lesson.tsx` procura a lição no catálogo **ou** na coleção e espera a coleção carregar antes de concluir que a lição não existe (deep link). Uma aula do baú **não** entra na conta de "área concluída" dos emblemas: o catálogo que o `isAreaComplete` lê nunca a traz.
- **A loja não tem log offline nem desfaz compras.** **Compra, dica e leitura da loja têm timeout** (`PURCHASE_TIMEOUT_MS` 20 s — acima dos 15 s da transação no servidor, para ele já ter decidido quando o app desistir —, `READ_TIMEOUT_MS` 10 s): o `apiClient` não tem timeout próprio, e sem teto um servidor que não responde deixaria o modal em "carregando" para sempre. Uma compra ou dica **sem resposta** (rede ou timeout) relê o estado da loja na hora, porque o servidor pode ter cobrado. `buyItem` também **espera um envio da fila já em andamento** (até 10 s) em vez de recusar com um `pending_sync` falso: o `flushQueue` retorna na hora quando já há um envio, com os eventos ainda em `syncing`. O rótulo "Ativo até" usa o idioma do app (pt em 24 h) e some sozinho no fim da janela (um `setTimeout` re-renderiza a tela). Se a resposta de uma compra se perder na rede (o servidor cobrou, o app não soube), o próximo `refreshShop` (ao focar a loja ou abrir o desafio de código) corrige tudo: adota o saldo do servidor quando não há evento por enviar (com pendentes o saldo local está à frente de propósito) e invalida a coleção guardada se ela tem menos aulas do que o servidor diz que foram reveladas (`chest.areas[].revealed`) — vale também para uma aula revelada em outro aparelho. Depois de um baú comprado (e de um 409 `boost_active`) o app já relê o estado sozinho. O app nunca "repete" uma compra sozinho.
- **Sem emulador**: a lógica (SQLite, dobro de XP, ações da loja) foi exercitada com o harness descartável descrito em "XP, níveis e Bits"; as telas (Market, lista com aulas do baú, botão de dica) só foram verificadas por tipo — a conferência visual no emulador continua pendente.

## Lembretes de inatividade (notificações)

Quem fica sem abrir o app recebe notificações locais calorosas, com texto sorteado, **desde que o recurso esteja ligado** (switch em Configurações, `NotificationSwitcher`).

- **Locais e agendadas, não push.** Funcionam offline, sem backend. O texto de uma notificação agendada é fixo, então o sorteio acontece no momento de agendar.
- **Três lembretes por ausência: 7, 14 e 30 dias** (`REMINDER_DAYS` em `NotificationService.ts`), cada um com uma mensagem diferente (`pickReminderMessages`, sorteio sem repetição dentro da rodada). Depois do dia 30, silêncio. As mensagens vivem em `notificationService.reminders` (array de `{title, body}`) em `pt.json`/`en.json` — são texto de UI, não conteúdo pedagógico.
- **Não existe "última atividade" gravada** (sem streak, `UserLessons` não tem timestamp). Em vez de criar uma, o app **re-arma**: `armInactivityReminders()` cancela os três e agenda de novo a partir de agora, ao abrir o app e a cada mudança de `AppState`. Se a pessoa não volta, o último agendamento é o que dispara. Os identificadores são fixos (`inactivity-reminder-<dias>`), então re-armar nunca acumula.
- **Cancelar e armar passam por uma fila** (`enqueue`) — sem ela, um logout (cancelar) e um retorno ao primeiro plano (armar) disparados juntos podiam intercalar e deixar lembretes de uma conta deslogada.
- **Quem decide é um hook só, `useInactivityReminder` (chamado em `App.tsx`)**, reagindo a `AuthStore.isLoggedIn` + `NotificationStore.enabled`. Por isso logout manual e sessão expirada (ambos viram `isLoggedIn=false`) cancelam os lembretes sem tocar em `User.tsx` nem no efeito de sessão. Trocar o idioma re-arma (`language` na dependência).
- **Preferência**: `NotificationStore.enabled` é `undefined` (ainda não hidratada), `null` (nunca decidiu) ou `boolean`. O `undefined` existe porque a hidratação roda num efeito do `App` no mesmo commit do hook: sem ele, o primeiro login pediria a permissão em cima de uma escolha já gravada. O padrão é **ligado**: no primeiro login com a preferência `null`, o hook pede a permissão do sistema — aceitou, `true`; negou, `false` (o switch reflete). `setEnabled` já persiste em AsyncStorage.
- **Ligar pelo switch** pede a permissão (`ensureNotificationPermission`); se negada, o switch fica desligado e mostra o alerta global `alert.notification`. `armInactivityReminders` nunca pede permissão — sem ela, simplesmente não agenda.
- **Sem o módulo nativo (Expo Go no Android)** `areNotificationsAvailable()` é `false`: o hook não pede permissão nem grava a preferência (não se grava "desligado" por limitação do ambiente) e o switch de Configurações não faz nada.
- Em primeiro plano nenhuma notificação é exibida (`setNotificationHandler`): o lembrete só faz sentido com o app fechado.
- **Não implementado de propósito**: abrir uma tela específica ao tocar na notificação (abrir o app já leva à Home), horário preferido/"não perturbe", ícone monocromático de notificação (o plugin aceita `icon`, mas não há um PNG branco 96×96 no repositório — no Android a barra de status usa o ícone padrão), e re-sincronizar o switch se a permissão for revogada nas configurações do sistema depois de aceita.

## Design system (componentes `Themed*`)

`src/components/themed/*` (`ThemedView`, `ThemedText`, `ThemedTouchableOpacity`, `ThemedIcon`, `ThemedLine`, `ThemedAlert`, `ThemedHighlighter`, `ThemedSkeleton`) são wrappers finos sobre os componentes nativos/`react-native-paper` que recebem uma prop `theme` (`"primary" | "background" | "card" | "text" | "border" | "notification"`, com default sensato) e resolvem a cor via `useTheme().colors` do `@react-navigation/native`, aplicada sobre `LightMode`/`DarkMode` (`src/theme/*.ts`). **Prefira sempre esses componentes a `View`/`Text`/`TouchableOpacity` nativos quando a cor deve reagir ao tema** — algumas telas mais antigas ainda usam cores hardcoded e componentes nativos diretamente; isso é dívida existente, não o padrão a seguir em código novo.

**Peças compartilhadas de Perfil, Configurações, login e modais** (`src/components/`), todas lendo `useTheme().colors` + `useAppColors()`: `ListRow` (linha de lista em cartão `primary` com ícone em quadrado tingido, seta, `right` para `Switch`, `selected` para a opção escolhida de uma lista e `danger` para ação destrutiva; aceita `onLongPress`/`delayLongPress`/`onPressIn`/`onPressOut`), `AppModal` (casca de todo modal: véu, cartão `primary` com cantos de 24, título + X, `scroll` para corpo longo, `footer` para ações, `hideClose` para avisos; fecha tocando fora, no X ou no voltar — a altura vem do conteúdo, nada de altura em porcentagem; o fundo que fecha é irmão do cartão, não pai dele, senão a rolagem do corpo não pega; com `scroll`, um degradê da cor do cartão aparece em cima e/ou embaixo só do lado que ainda tem conteúdo), `AppButton` (50 dp, cantos 20, `primary`/`secondary`, `loading`), `TextField` (campo com rótulo fixo, 52 dp, contorno que vira cor de ação em foco e vermelho em `error`; `revealable` põe o olho que mostra/oculta a senha, com os rótulos de acessibilidade `showPassword`/`hidePassword`), `Flag` (bandeira do Brasil ou dos EUA desenhada em SVG com `react-native-svg`, não emoji; aparece no seletor de idioma e na linha "Idioma" das Configurações). `ThemedAlert` e `ComingSoon` são `AppModal`s. O seletor de área das Aulas é o `AreaSelector`: um cartão que desce do cabeçalho, com ícone, nome e marca de seleção. Os modais do Mercado (`MarketModal`) e da galeria escondida ainda têm casca própria. `brandText` (texto de marca legível no tema: `#9AA5FF` no escuro, `#4357C7` no claro) é para título de seção e link; o índigo `#5469D3` cru dá só 3,5:1 sobre o escuro.
- **Tema claro** (`LightMode.ts`, `appColors.ts`, `theoryTheme.ts`): é a contraparte "luz do dia" do azul-marinho do escuro, desenhada à parte — não é o escuro invertido. Mesma família de matiz (neutros azulados, nunca cinza puro nem branco chapado) e a mesma marca índigo `#5469D3`; a elevação segue a lógica do escuro (a superfície elevada é **mais clara** que a tela). Papéis do React Navigation: `background` `#F3F6FB` (tela azul-gelo), `primary` `#FFFFFF` (cartões, itens de lista, modais, barra de abas), `card` `#E8EEF7` (superfície rebaixada), `border` `#CCD6E6`, `notification` `#E1E8F3`, `text` `#141F29` (a tinta é o fundo do escuro; 15,4:1 na tela). O que não cabe nesses papéis vive em `useAppColors()` (`src/theme/appColors.ts`): `brand`, `action` (fundo de botão: `#637aff` no escuro; **`#5469D3` no claro**, porque branco sobre `#637aff` dá só 3,65:1), `onBrand` (texto sobre a marca: `#F1F1F1` no escuro, branco no claro), `brandText`, `muted`, `rule`, `tabIdle`/`tabActive`, `fieldBorder`/`fieldBackground`/`fieldText`, `scrim`/`scrimInner` e as cores de login/cadastro (`canvas`, `sheet`, `shade`, `authAccent`, `authPlaceholder`). **Regra de ouro: o valor de cada token no escuro é exatamente o literal que já estava no código** — o tema escuro não foi alterado (conferido por comparação de pixels antes/depois em 24 telas) e todo ajuste de componente é um ramo `!app.isDark`. Contrastes (WCAG 2.x) calculados contra a superfície onde cada cor aparece estão documentados nos comentários dos arquivos. **Armadilhas que o claro revelou:** (1) `ThemedTouchableOpacity`/`ThemedView` aplicam a cor do tema **depois** do `style`, então um `backgroundColor` passado no `style` nunca vale — o botão "Executar" do terminal da teoria era `primary` (aço no escuro, **branco no claro, com texto branco**) e só agora tem fundo próprio; (2) texto sobre fundo de marca precisa de `useCustomColor` + `app.onBrand`, senão herda `colors.text` (preto no claro); (3) `primary` branco some como esqueleto de carregamento (`ThemedSkeleton` usa `card` no claro) e como botão de modal (`ValidationModal`, `ContentUpdateModal` usam `app.action` no claro); (4) o fio padrão de `ThemedLine` é a cor do texto — no claro vira `app.rule`. Tons vivos do escuro (verde, âmbar, dourado) ficam abaixo de 3:1 sobre o claro: a paleta da teoria tem `success`/`danger`/`warning`/`gold` próprios para cada tema. **Dourado do desafio no claro:** um amarelo vivo nunca chega a 4,5:1 como texto sobre claro (o amarelo é claro demais), então os papéis se separam — `gold` `#C28A00` (vivo, só borda e ícone: o troféu e a borda da lição-desafio no `ClassButton`, 3,0:1 no branco) e `goldInk` `#7F5600` (o texto), este sempre sobre uma **etiqueta dourada** (`goldLabel(palette)` em `theoryTheme.ts`: fundo `goldBg`, borda `goldBorder`, texto 5,4:1) usada no selo "Desafio do módulo" e no "Ainda não funcionou" do playground e do desafio. No escuro `goldLabel` devolve `null` e `gold`/`goldInk` são o mesmo dourado de antes — a tela não muda. O texto em índigo `#5469D3` sobre a tela dá 4,47:1 — aceito apenas em texto grande/negrito (títulos de seção e de modal); texto pequeno em marca usa `app.brandText` (`#4357C7`, 5,7:1).
- `ThemedSkeleton` (`width`/`height`/`borderRadius`/`theme`) é o placeholder padrão para estados de carregamento — um retângulo com "respiração" de opacidade via `react-native-animatable` (`animation` como objeto de keyframes customizado, `iterationCount="infinite"`; já era dependência do projeto, usada assim em `TabButton.tsx`, então não foi adicionada uma lib de skeleton nova). Use-o (em vez de um `ActivityIndicator` ou de não renderizar nada) sempre que uma tela tiver uma `useQuery` cujo `isPending` deva cobrir com um placeholder do mesmo tamanho/formato do conteúdo final, evitando pulo de layout — ver uso em `Classes.tsx`/`AreaModules.tsx` abaixo.

Layout: `CenterView`, `RowView`, `ColumnView` (`src/components/layout`) são primitivas de flex reutilizáveis — prefira-as a recriar `View` com `style={{ flexDirection: ... }}` ad-hoc.

**Abas (Aulas, Mercado, Perfil, Configurações)**: o cabeçalho é o `ScreenHeader` (chapado, na cor da tela, sem borda nem sombra; o respiro acima do título é a altura da barra de status — `useInsets().top` — mais 6 dp, via `useHeaderTopPadding()`, porque um valor fixo deixava o título colado nas notificações em aparelhos de barra alta como o A52; quem precisa da altura do cabeçalho, como o esqueleto de `Classes` e o `AreaSelector`, soma isso a `HEADER_ROW_HEIGHT`; `footer` opcional, usado pelo nível do perfil) e a separação do conteúdo é um degradê, não uma linha — `EdgeFade edge="top"` logo abaixo do cabeçalho (`HEADER_FADE`, 28 dp) e, por trás da barra de abas, o degradê de baixo que o `TabNavigation` renderiza num `tabBar` customizado (cobre a faixa da barra e esmaece `TAB_BAR_FADE` dp acima dela). Para isso a rolagem de cada aba **vai até a borda da tela** e reserva o espaço da barra com `paddingBottom: TAB_BAR_CLEARANCE` (`tabBarMetrics.ts`) — não use mais `marginBottom`/altura em porcentagem para desviar da barra. O degradê usa `colors.background` com alfa `00` (não `"transparent"`, que no Android interpola por preto) e vale nos dois temas. Telas novas numa aba seguem o mesmo molde: `ScreenHeader` + `<View flex:1>` com a rolagem e o `EdgeFade` por cima.

## Conteúdo de aulas (`screens/classes`)

- **Áreas, módulos, lições e atividades vêm todos da API** (`GET /areas`, `GET /modules` — ver `api/CLAUDE.md`, seção "Conteúdo pedagógico"), numa chamada só por área. `Classes.tsx` busca as áreas (`useAreasQuery`) e guarda só a escolha explícita do usuário (`pickedAreaId`, `useState`); a área efetiva é **derivada** (`pickedAreaId ?? areas?.[0]?.id`), não sincronizada por `useEffect` — a padrão é `areas[0]` (a primeira retornada por `GET /areas`, sempre HTML, já que o seeder cria nessa ordem e a API ordena por `id asc`). Derivar importa: com o prefetch do boot (ver abaixo) as áreas já estão em cache no primeiro render, e um `useEffect` só definiria a área um render depois — fazendo `AreaModules` montar uma vez com `areaId` indefinido e registrar uma entrada de cache órfã `["modules", undefined, <lang>]`. Renderiza `AreaModules`, que busca os módulos da área selecionada (`useModulesQuery`) e um `ModuleCard` por módulo retornado.
- **Áreas não são traduzidas** — `useAreasQuery()` não recebe idioma e sua key é só `["areas"]` (um cache só, válido para qualquer idioma), porque `GET /areas` não recebe `locale`: nomes de área são termos técnicos (HTML, CSS, JavaScript). Já `useModulesQuery(areaId, language)` **é** por idioma (key `["modules", areaId, language]`), já que módulos são traduzidos. Não adicione idioma de volta à key de áreas.
- **Conteúdo de aulas é exclusivamente vindo da API — nunca do i18n.** `src/translations/i18n/locales/{pt,en}.json` guardavam, até pouco tempo atrás, um volume grande de textos de lições/exercícios/nomes de botão hardcoded (um `html`/`js`/`css` aninhado inteiro com pergunta/opções por exercício, um array `TESTE` de lições de exemplo, um objeto `tutorial` para um componente `Tutorials` que nem existe mais no projeto, e dezenas de chaves soltas tipo `title1`-`title4`/`paragraph1`-`paragraph4`) — resíduo de antes da API existir, sem nenhuma referência viva no código (confirmado varrendo todo `t(...)` do app antes de remover). Foi tudo removido; os dois arquivos hoje só têm textos de UI genuína (configurações, perfil, mercado, login/registro, alertas, info do app) que não têm — e não devem ter — equivalente na API. Ao adicionar/editar conteúdo de lição, sempre pelo seed (`api/prisma/seed.ts`) — nunca crie uma chave de i18n para texto de aula.
- **`buster` do cache persistido**: `persistOptions.buster` (`App.tsx`) é uma string que, ao mudar, faz o `PersistQueryClientProvider` **descartar todo o cache persistido** na próxima abertura. Como `gcTime` é `Infinity`, uma entrada num formato que não existe mais nunca seria coletada sozinha e ficaria para sempre no AsyncStorage. **O papel disto mudou**: mudança de **conteúdo** não exige mais bump — quem invalida o cache quando uma lição muda é `content_version` (ver abaixo), e é isso que permite conteúdo novo sem release do app. O bump continua **obrigatório quando o formato da query key OU do dado persistido mudar**, caso em que o app foi recompilado de qualquer jeito e o cache antigo tem uma forma que o código novo não sabe ler. Regra prática: mexeu no seed/dashboard, publique uma `content_version`; mexeu num tipo de `contracts.ts` ou numa query key, bumpe aqui. O histórico abaixo é anterior a esse mecanismo — vários daqueles bumps (5, 7, 9, 10, 12) hoje seriam uma publicação de versão. O bump `4` foi o primeiro por mudança **de dado** e não de key: a key `["modules", areaId, language]` não mudou, mas o payload passou a incluir `lessons[].activities[]`, e sem o bump quem já tinha o app ficaria com uma lista de lições vazia para sempre. O bump `5` é do mesmo tipo: as 2 lições de teste do primeiro módulo de HTML foram substituídas pelas 8 lições reais do módulo básico (ver `api/CLAUDE.md`, "Conteúdo pedagógico") — mesmo formato de dado, conteúdo diferente. O bump `6` cobre dois motivos juntos: os primeiros módulos de CSS e JavaScript ganharam lições reais (antes vinham com `lessons: []`), e `TheoryActivityContent` ganhou o campo opcional `additionalCode` (ver abaixo). O bump `7` é do mesmo tipo do `5`: os **segundos** módulos (intermediário) das três áreas ganharam lições reais (antes vinham com `lessons: []`) — mesma key, mesmo formato, conteúdo novo; sem o bump, quem já tinha aberto o app ficaria com o módulo 2 vazio para sempre. O bump `8` cobre dois motivos juntos, do mesmo tipo dos anteriores: os **terceiros** módulos (avançado) das três áreas ganharam lições reais, e `codeLanguage`/`additionalCode[].codeLanguage` ganharam `'TypeScript'` como valor aceito (usado pelas lições de TypeScript do módulo avançado de JavaScript). O bump `9` é do mesmo tipo do `5`: o conteúdo seedado no bump `8` para o módulo 3 (avançado) das três áreas seguia uma proposta curricular errada (JavaScript incluía Node.js/Express, que o projeto reserva para um módulo futuro) e foi inteiramente substituído — mesma key, mesmo formato, conteúdo diferente; sem o bump, quem já tinha aberto o app com o bump `8` ficaria preso no conteúdo errado do módulo 3 para sempre. O bump `10` é do mesmo tipo do `5`/`7`: o quarto módulo de JavaScript ("Além do JavaScript: Node.js e Express") ganhou lições reais (antes vinha com `lessons: []`) — o `name` do módulo em si continua genérico ("Módulo 4"/"Module 4", igual HTML/CSS, que ainda não têm conteúdo nesse módulo). Sem o bump, quem já tinha aberto o app ficaria com o módulo 4 de JavaScript vazio para sempre. O bump `11` é do mesmo tipo do `4`: `ModuleResponse` ganhou o campo `subtitle` — o nome descritivo de cada módulo ("Além do JavaScript", "HTML avançado" etc.), que antes vinha hardcoded no app (`areaMetadata.ts` + i18n, por posição — ver abaixo), agora vem de `module_translations.subtitle` (ver `api/CLAUDE.md`, "Conteúdo pedagógico"); mesma key, payload novo. Sem o bump, quem já tinha aberto o app ficaria com o subtítulo de todo módulo em branco para sempre. O bump `12` é do mesmo tipo do `10`: os quartos módulos de HTML ("Além do HTML: introdução ao React") e CSS ("Além do CSS: Tailwind CSS e Ecossistema") ganharam lições reais (antes vinham com `lessons: []`) — sem o bump, quem já tinha aberto o app ficaria com esses dois módulos vazios para sempre.
- **Atualização de conteúdo sob demanda (`content_version`)** — `useContentVersionSync` (`src/hooks/`, montado por `src/components/ContentVersionSync.tsx`) pergunta à API a versão publicada do **idioma atual**, compara com a guardada e, se **divergir**, invalida o cache do catálogo. É o que faz conteúdo editado no dashboard chegar ao usuário **sem release do app**. Pontos que não devem ser desfeitos sem entender o porquê:
  - **Compara por diferença, não por "maior" — e pelo `id` da publicação, não pela string.** Cobre rollback (que é uma linha nova, com `id` maior mesmo que o número de versão seja menor) e evita comparação semver no cliente — `"0.0.10" > "0.0.9"` é falso como string. O formato antigo da chave (só a string) ainda é lido e comparado pela string, para quem atualiza o app não rebuscar o catálogo só pela troca de formato (`needsRefetch`).
  - **Só o idioma atual é invalidado** (`isStaleForLanguage`, exportada do hook justamente para poder ser conferida isolada). Um idioma com suporte parcial não deve rebuscar porque outro mudou. As áreas (`["areas"]`, sem idioma na key) acompanham qualquer publicação: uma área nova pode ter conteúdo só no idioma publicado, e mostrá-la antes disso renderizaria nomes vazios.
  - **A versão só é gravada DEPOIS do refetch terminar.** Gravar antes seria uma falha permanente e silenciosa: com a rede caindo no meio, o app ficaria com versão nova e conteúdo velho, a comparação seguinte daria "igual" e ele nunca mais se corrigiria. Falhando, a versão guardada continua a antiga e o próximo boot tenta de novo.
  - **Roda dentro do `PersistQueryClientProvider` e só depois de `useIsRestoring`.** Invalidar durante a restauração do cache persistido é corrida com ela — mesmo motivo pelo qual o prefetch de áreas mora no `onSuccess` do provider. Daí o componente-invólucro: os outros hooks de boot são chamados no corpo de `App`, que fica fora do provider.
  - **Nunca bloqueia nem alerta.** Sem rede, com a API fora do ar ou sem versão publicada para o idioma, não faz nada e o usuário segue fazendo aula offline com o cache.
  - **A consulta tem timeout próprio de 4s** (`VERSION_REQUEST_TIMEOUT_MS`). O `apiClient` não define `timeout` e o padrão do axios é `0` (infinito), então numa rede que aceita a conexão e não responde (portal cativo, servidor pendurado) a promise ficaria viva pelo resto da vida do app. Um teto curto cobre todos os modos de falha com um mecanismo só — checar conectividade antes não bastaria, porque "conectado" não é "alcançável". **O limite é só desta consulta**: o catálogo (~150 KB) pode legitimamente demorar mais numa rede lenta e não deve herdá-lo.
  - A versão local fica em **AsyncStorage** (`"ContentVersions"`, um JSON por idioma), não no SQLite. O argumento decisivo não é simplicidade: é que o cache do React Query que ela protege **também** vive em AsyncStorage, então os dois somem juntos. Em SQLite, um `clear()` da AsyncStorage apagaria o cache e deixaria a versão para trás — o app concluiria que está atualizado sem ter conteúdo nenhum.
- **Lição concluída que depois é removida do catálogo.** O que foi verificado: o registro órfão em `UserLessons` é inofensivo na interface (nunca casa com lição renderizada) e um evento de `/sync` que falha por FK inexistente é marcado como `failed`, terminal — **não** entra em retry infinito. A divergência de XP que isso causava (o usuário pontuou localmente por uma lição que o servidor nunca vai registrar) agora se corrige sozinha: um evento `failed` não impede o app de adotar o valor do servidor quando a fila esvazia (ver "XP, níveis e Bits"). A remoção de conteúdo pelo dashboard torna o cenário possível na prática.
- **Aviso de conteúdo atualizado** (`ContentUpdateModal`, na aba de aulas). Mostra a versão mais recente e as notas do que chegou desde a última vez que a pessoa foi avisada: a mais nova em destaque, até mais duas anteriores e "e mais N" (`MAX_EARLIER`). Decisões que não devem ser desfeitas sem entender o porquê:
  - **Dois marcos por idioma, não um**: `syncedId` (o conteúdo que o cache reflete) e `seenId` (a última publicação de que a pessoa foi avisada). Num número só, o aviso teria de aparecer no exato momento da atualização — que roda em segundo plano, possivelmente no meio de uma lição. Separados, o conteúdo troca quando chega e o aviso espera. O que fica entre os dois continua pendente mesmo se o app for fechado antes do aviso.
  - **Quem busca as notas é a sincronização; quem mostra é a aba de aulas.** Depois de gravar o `syncedId`, `useContentVersionSync` chama `refreshPendingAnnouncements`, que pede `GET /content-version?locale=&sinceId=<seenId>`, filtra só as publicações com `announce` e guarda as notas na própria chave. Por isso o aviso abre instantâneo e sem rede. Falhar nessa consulta não desfaz a atualização do conteúdo — a próxima sincronização tenta de novo; e ela é barata de chamar sempre, porque não faz nada quando não há pendência ou quando as notas até a versão atual já foram buscadas. Uma publicação mais nova que o `syncedId`, saída entre as duas consultas, fica de fora: o conteúdo dela ainda não foi rebuscado.
  - **Lê só no foco da aba** (`useContentAnnouncement`, `useFocusEffect`), nunca em reação à sincronização terminar. Assim o aviso aparece ao abrir o app ou ao voltar de uma lição — pausas naturais — e nunca no meio de uma lição ou da rolagem. Se a sincronização terminar com a pessoa já na aba, o aviso espera a próxima entrada nela.
  - **Informa, não decide.** O conteúdo já foi atualizado quando o aviso aparece; fechar não desfaz nada. Um botão só ("Entendi"), nunca "deseja atualizar?" — se dispensar significasse não atualizar, quem sempre dispensa ficaria preso em conteúdo velho.
  - **Nunca aparece na primeira instalação nem na primeira vez num idioma**: sem estado anterior, o estado já nasce visto (`nextSyncedState`) — um aviso de novidades para quem nunca viu o conteúdo anterior é ruído. O **formato antigo** da chave (só a string, de antes do aviso) recebe o mesmo tratamento: é convertido sem aviso.
  - **Publicação sem `announce` é silenciosa.** É decidido no dashboard ("Avisar os alunos"); o padrão da coluna é falso, então as publicações anteriores ao aviso — inclusive notas técnicas sem acento de setembro — nunca aparecem para ninguém. Se tudo no intervalo foi silencioso, `seenId` avança direto e nenhum aviso é mostrado.
  - **`seenId` só anda para frente** (`Math.max` em `markAnnouncementsSeen`), e as escritas na chave passam por uma **fila** (`updateStoredContentState`): sincronização e aviso fazem ler-alterar-gravar no mesmo JSON, e duas intercaladas apagariam uma a outra (o aviso fechado na hora em que a sincronização grava regravaria um `syncedId` antigo).
  - O changelog é **escrito para o aluno** — é exatamente o texto que aparece. Chaves i18n em `contentUpdate.*` (o "e mais N" usa `moreOne`/`moreMany` em vez de plural do i18next, que dependeria de `Intl.PluralRules`).
- **Descartado — buscar a versão durante o boot.** A ideia era disparar a consulta em paralelo com as leituras de AsyncStorage, para a resposta já estar em mãos quando a UI pintasse. Medido: o payload da consulta é ~105 bytes, enquanto o cache persistido são ~147 KB por idioma; e invalidar antes de `isRestoring` liberar é a corrida descrita acima, então buscar cedo só sobrepõe a latência à restauração. Tinha ficado para revisitar quando o aviso existisse, porque aí o atraso seria visível. **Não é mais necessário:** o aviso lê notas já guardadas e aparece no foco seguinte da aba, nunca em reação à sincronização — não há nada esperando a consulta chegar.
- **`app_version` e `content_version` são eixos diferentes — não misturar.** `content_version` diz "há conteúdo novo"; `app_version` (tabela que já existe, com `need_update`, ainda sem uso) diria "seu app é velho demais para este conteúdo". O caso real que vai exigir a segunda: conteúdo novo usando um `type` de atividade que o app instalado não sabe renderizar — `filterPlayable()` descarta em silêncio e o aluno recebe uma lição com menos telas sem entender por quê.
- **Nunca chame `useModulesQuery` com `areaId` indefinido** — uma query desabilitada por `enabled` **ainda registra a entrada no cache**, então isso deixava um `["modules", undefined, <lang>]` órfão permanente. Por isso `useModulesQuery` exige `areaId: number` e `Classes.tsx` renderiza `ModuleListSkeleton` (em vez de montar `AreaModules`) enquanto a área não foi resolvida. `ModuleListSkeleton` é compartilhado por esse caso e pelo `isPending` de `AreaModules`, então o placeholder é idêntico nos dois — não há flash nem markup duplicado. Aplique o mesmo cuidado ao criar qualquer query nova com parâmetro assíncrono.
- **Prefetch das áreas no boot**: `App.tsx` chama `queryClient.prefetchQuery(areasQueryOptions())` no `onSuccess` do `PersistQueryClientProvider` — ou seja, logo depois que o cache persistido termina de restaurar, nunca antes (prefetchar durante a restauração deixaria os dois escrevendo na mesma entrada em ordem indefinida). É fire-and-forget de propósito: o retorno **não** é devolvido do `onSuccess`, senão o provider esperaria a rede antes de liberar o `isRestoring`, e a splash nunca depende de conexão. Com `staleTime: Infinity`, vira no-op quando as áreas já vieram do cache — na prática só busca de fato na primeira instalação. As opções ficam em `areasQueryOptions()` (exportado de `useAreasQuery.ts`), compartilhadas entre o hook e o prefetch para os dois não popularem entradas de cache diferentes.
- **Skeletons enquanto carrega**: `Classes.tsx` mostra um `ThemedSkeleton` no lugar do `ClassHeader` enquanto `useAreasQuery` está `isPending`; a lista de módulos usa `ModuleListSkeleton` (`components/ModuleListSkeleton.tsx`, 4 `ThemedSkeleton` no mesmo tamanho/margens de um `ModuleCard` real, para não pular o layout quando o conteúdo chega; o esqueleto usa `width="auto"`, porque com a largura padrão do `ThemedSkeleton` (100%) as margens laterais o empurravam 40 dp para fora da tela) em dois momentos: `Classes.tsx` enquanto a área ainda não foi resolvida e `AreaModules.tsx` enquanto `useModulesQuery` está `isPending`. Como `staleTime`/`gcTime` são infinitos e o cache é persistido, isso só aparece de fato no primeiro carregamento de cada dispositivo — em aberturas seguintes o cache já hidrata com dado antes mesmo do primeiro render.
- **`areaMetadata.ts`** (`src/screens/classes/areaMetadata.ts`) é o mapeamento manual de ícone/cor (por área) e imagem (por módulo) — **por posição no array**, não pelo `id` do Postgres: o `id` é um autoincrement sem valor previsível (não é resetado por um `DELETE`, então nunca vale supor `1`/`2`/`3`), mas a posição é estável porque o seeder sempre cria as áreas na mesma ordem (HTML, CSS, JavaScript) e `GET /areas` sempre ordena por `id asc`. `getAreaIndex(areas, areaId)` faz essa tradução `id` → posição; `Classes.tsx` e `AreaModules.tsx` usam sempre essa função, nunca comparam um `id` literal. Ao adicionar uma área/módulo novo no seeder, adicione a entrada correspondente em `areaMetadata.ts` na mesma posição. **O nome descritivo de cada módulo (`ModuleCard`'s `subtitle`, ex.: "Além do JavaScript") não mora mais aqui** — até o bump `11` vinha de um `subtitleKey` mapeado por posição + i18n local, igual a imagem; hoje vem direto de `module.subtitle` (API, `module_translations.subtitle`), porque é conteúdo pedagógico real, não cosmético — só imagem/ícone/cor continuam hardcoded aqui, por não terem coluna própria no banco (ver `api/CLAUDE.md`).
- **Cada lição abre numa rota dedicada, não num modal**: `AreaModules.tsx` renderiza um `ClassButton` por item de `module.lessons` (ou `LessonComingSoon` se o módulo ainda não tem lição), navegando para `Lesson` com `{ areaId, moduleId, lessonId }`. A tela `screens/classes/Lesson.tsx` recebe **só ids** e redescobre a lição no cache de `useModulesQuery` (mesma query key da tela de aulas) — por isso não dispara requisição nova, funciona aberta direto por deep link e continua no idioma certo se o usuário trocar de idioma com a tela na pilha. Não passe o objeto da lição como param: params de deep link só carregam primitivos.
- **`ActivityPlayer.tsx` é o stepper compartilhado** — percorre as N atividades, calcula o progresso e despacha cada uma pelo `type` para o renderizador registrado em **`ACTIVITY_REGISTRY`** (`activityRegistry.tsx`, um `Record<type, render>`: `theory`, `option`, `code_blank`, `fill_blank`, `code_playground`, `code_editor`, `reorder`, `matching`). A registry substituiu o `switch` + `SUPPORTED_TYPES` quando o app chegou a 5 tipos, como previa o [roadmap](../docs/roadmap-atividades-praticas.md). Quem monta a casca é a tela `Lesson` (rota) ou o `ClassView` (modal do conteúdo de teste); os dois usam o mesmo player, então essa lógica não é duplicada. **Para suportar um tipo novo, basta uma entrada na registry** — `filterPlayable()` descarta o que não está nela antes de entrar no player, para uma atividade desconhecida não travar o usuário numa etapa em branco (e para a barra de progresso não mentir). É também o que deixa uma versão antiga do app conviver com um tipo novo no banco: a lição só mostra uma atividade a menos. O teste usa `hasOwnProperty`, não `in` — um `type` `"constructor"` acharia o protótipo do objeto. Cada renderizador recebe `activityKey` e o põe no `key` do componente (ver abaixo).
- O `content` de cada atividade vem tipado do contrato compartilhado (`TheoryActivityContent`/`OptionActivityContent` em `codap-api/src/types/contracts`), e `Theory`/`Option` em `types/entities.d.ts` são **derivados desses mesmos tipos** — a galeria de atividades (`activityGallery.ts`) e o conteúdo da API não podem divergir sem quebrar o build. `correctOption` é **1-based** (`OptionExercise` compara com `correctOption - 1`); não normalize para 0-based.
- **Teoria fixa, prática sorteada**: `Lesson.tsx` não entrega `lesson.activities` direto ao player — passa por `buildLessonSession()` (`app/src/utils/buildLessonSession.ts`, função pura). A teoria (`type === "theory"`) vem primeiro, na ordem do `index`, e nunca é aleatorizada. A prática vem depois: atividades com o mesmo `content.pool` são alternativas entre si e a sessão sorteia `draw` delas (lido da primeira do pool; default 1; sem `pool` = sempre aparece), a lista de prática é embaralhada, e cada `option` sem `fixedOrder` tem as alternativas embaralhadas com o `correctOption` remapeado para a nova posição — por isso o conteúdo grava a correta sempre na posição 1 sem problema. **Verdadeiro/falso não é um tipo novo**: é uma `option` com duas alternativas ("Verdadeiro"/"Falso") e `fixedOrder: true`, para os botões não trocarem de lugar. A função devolve objetos novos e nunca muta a entrada (que é o cache do React Query). O sorteio fica num `useMemo` por `[lesson?.id, language]` — um refetch que devolve a mesma lição não re-sorteia no meio da sessão; trocar o idioma re-sorteia, e o `key` do `ActivityPlayer` (`${lessonId}-${language}`) zera o índice junto. O `ClassView` (conteúdo de teste) não passa por ela.
- **`key={activityKey}` nos exercícios da registry** é obrigatório: sem ele, duas `option` seguidas reaproveitam a mesma instância de `OptionExercise` e a segunda herda a alternativa marcada e o estado do modal da primeira.
- **Trecho de código no enunciado da `option`**: `OptionActivityContent.code?`/`codeLanguage?` (opcionais, default `JavaScript`) fazem o `OptionExercise` mostrar o trecho entre o enunciado e as alternativas, via `CodeSnippet.tsx` (`app/src/screens/classes/components/`). **Não é o `CodeSection` de propósito**: aquele tem altura fixa, aba "Web" e o botão "Executar" do terminal — num "qual a saída?", rodar o código entregaria a resposta. O `CodeSnippet` é só leitura (`CustomSyntaxHighlighter` com as mesmas cores do `CodeSection`), acompanha a altura do trecho e rola na horizontal em linhas longas, em vez de quebrá-las. A rolagem é só uma rede de segurança (fonte aumentada no app): o conteúdo é autorado com no máximo 30 caracteres por linha (ver `api/CLAUDE.md`), então no tamanho padrão nada precisa rolar. Não dá para trocar por quebra automática sem mexer no `NativeSyntaxHighlighter`, que monta o código dentro de uma rolagem horizontal e também é usado pelo `CodeSection` da teoria.
- **`code_blank` — completar código tocando em blocos** (`CodeBlankExercise.tsx`, estilo Grasshopper): o `code` traz de 1 a 3 lacunas marcadas por `___`; o banco de blocos é `answers` + `distractors`, embaralhado uma vez por atividade (o `key` do `ActivityPlayer` remonta o componente a cada atividade). Com várias lacunas, cada toque preenche a próxima vazia na ordem do código e tocar numa lacuna preenchida devolve o bloco; com uma lacuna só, tocar noutro bloco troca a resposta. Os blocos são identificados pela posição no banco, não pelo texto (duas respostas iguais, como `p` e `p` em `<p>...</p>`, continuam independentes). O código mostrado é o próprio `CodeSnippet` com os blocos já encaixados, e a correção compara cada lacuna com `answers[k]` usando o mesmo `ValidationModal`. Sem teclado de propósito: digitar `<`, `{` ou `;` no celular é a parte ruim de escrever código, não a parte a exercitar. Entra na `ACTIVITY_REGISTRY`; o `buildLessonSession` não precisou mudar, porque já trata como prática tudo que não é `theory` (inclusive `pool`/`draw`) — o mesmo vale para `reorder` e `matching`.
- **`fill_blank` — completar código digitando** (`FillBlankExercise.tsx`): o par "de lembrar" do `code_blank` (que é "de reconhecer", por blocos). O `code` tem uma lacuna só; o `TextInput` fica **abaixo** do `CodeSnippet`, e não dentro do código — no React Native um campo não flui no meio de uma linha de texto —, e o próprio snippet mostra o que está sendo digitado no lugar da lacuna. O teclado vem sem autocorreção, sugestões nem maiúscula automática (`autoCapitalize="none"`, `autoCorrect={false}`, `keyboardType="visible-password"`, que no Android tira a barra de sugestões): sem isso o celular trocaria `const` por `Const`. A correção é a função pura `isFillBlankCorrect` (exportada do mesmo arquivo): ignora espaços nas pontas, compara com qualquer item de `answers` e, com `ignoreCase`, ignora maiúsculas. O "Enter" do teclado também confere, porque com o teclado aberto o botão "Seguinte" fica escondido; antes do modal o teclado é fechado. Campo vazio não confere. A borda do campo em foco usa `palette.accent`. Chaves i18n em `fillBlank.*`; a dica interpola o rótulo real do botão (`t("next")`).
- **`code_playground` — playground guiado** (`CodePlaygroundExercise.tsx`, Fase 3a do roadmap): o aluno completa de 1 a 3 lacunas tocando em blocos (mesma mecânica do `code_blank`) e toca em **Executar**; o código roda de verdade numa WebView — **prévia visível** de HTML/CSS (170 px, rolável) e **console** em componente nativo embaixo. Para JavaScript sem `html` de apoio a WebView fica fora de tela, como no terminal. A correção é **pelo comportamento**: o `checkScript` autorado roda depois do código do aluno (no `DOMContentLoaded`, registrado no `<head>` — ver abaixo) e chama `__codap_report(passed, message?)`; qualquer combinação de blocos que funcione passa — a `solution` do contrato é só para autoria. Um `checkScript` que lança vira reprovação com a mensagem do erro; um que não chama o report mostra "o exercício não conseguiu conferir o resultado". Mudar um bloco invalida o resultado (precisa executar de novo), e o botão "Seguinte" só abre o modal depois de uma execução.
  - **Hardening (o código é do aluno):** `buildSandboxHtmlDocument({ checkScript, consolePanel: false, blockNetwork: true, loopGuardMs: 1000, forwardConsole: false })` — CSP sem rede (`default-src 'none'`, só `<script>`/`<style>` inline do próprio documento: `fetch` e imagens remotas falham) — e a **`SandboxWebView`** (`components/SandboxWebView.tsx`, compartilhada com o `code_editor`): `onShouldStartLoadWithRequest` que só deixa carregar o próprio documento (`about:blank`/`data:`), sem acesso a arquivo nem janelas novas, `cacheEnabled={false}`; quem usa a remonta a cada execução (`key`). Ela também exporta `parseSandboxMessage` (o resultado vem com a lista `checks` do `__codap_check`).
  - **Laço infinito — o watchdog não basta no Android.** Testado no emulador: um `while` sem fim com `console.log` dentro fez o **Expo Go parar de responder** (ANR). Dois motivos: desmontar a WebView **não interrompe** JavaScript em execução (o processo de renderização seguiu a 100% de CPU), e cada `console.log` da WebView vira uma mensagem para o processo do app, que se afoga. Por isso o playground usa **proteção de laços** (`protectLoops` em `codeSandboxDocument.ts`, a técnica do "loop protect" do CodePen): um scanner pequeno — que pula strings, template strings e comentários — põe a checagem na **condição** de cada laço — `while (x)` vira `while (__codapLoopGuard() && (x))`, `for (a; b; c)` vira `for (a; __codapLoopGuard() && (b); c)` — e no início do corpo de `for…in`/`for…of`; assim valem também laços sem chaves (`while (true);`) e o `while` do fim de um `do`. O relógio é **por tarefa**: conta desde a primeira volta de laço da tarefa atual e zera quando ela acaba (um `setTimeout(0)` guardado antes do código do aluno), então um laço num clique, minutos depois, ganha o próprio 1 s — um prazo único desde o carregamento cortaria qualquer laço de evento depois do primeiro segundo. A checagem lança "O laço foi interrompido" (também dentro de `<script>` que o aluno escreva no HTML; um laço `async` sem fim chega ao console pelo `unhandledrejection`); o console **não é repassado** ao nativo (`forwardConsole: false`) e guarda no máximo 500 entradas (erros ganham uma folga além disso, para a mensagem do laço sempre chegar). O app mostra só as últimas 40 linhas do console e, quando o laço foi interrompido, sobe essa causa para o destaque do resultado. O watchdog de 4 s continua como rede de segurança (um `while (` dentro de uma regex literal, por exemplo, escapa do scanner), e no timeout a WebView é desmontada. **Testado no emulador depois da correção:** o laço é cortado em ~1 s, o app fica a ~4% de CPU e a execução seguinte roda normal.
  - Chaves i18n em `playground.*` (o resto reaproveita `codeBlank.*` e `codeSection.*`).
- **`code_editor` — desafio do módulo** (`CodeEditorExercise.tsx`, Fase 3b do roadmap): o aluno **digita** o código, toca em **Executar** e vê a aba **Resultado** — prévia (200 px), a **lista de requisitos** ✓/✗ marcada pelo `__codap_check` do `checkScript` e o console.   - **`TheoryActivityContent.noTerminal?: boolean`** é o opt-out de conteúdo pra quando o código é elegível mecanicamente mas não produz nenhuma saída de console — só declarações/atribuições, ou algo que erraria/não mostraria nada de útil dentro da sandbox e não tem (ou não vale) um `terminalCode` simulado. Sem a flag, "Executar" sempre mostraria "Nenhuma saída de console.", ou pior, um erro de verdade. Encontradas varrendo as telas mecanicamente elegíveis por "não tem `console.` em lugar nenhum do código" (ou, no caso do módulo Node.js/Express, por usar API que não existe num engine de navegador), não por leitura manual de todo o módulo; uma tela nova de JS puro sem saída de console deveria ganhar a flag no mesmo padrão. Contagem e lista exata por módulo em `api/CLAUDE.md`, "Conteúdo pedagógico".
  - **WebView de execução é separada da aba "Web"** (`onlyCode: true` nunca tem aba "Web") e fica fora de tela (`position:"absolute", width:1, height:1, opacity:0`) — nunca `width:0`/`height:0` (histórico de pouca confiabilidade no Android: algumas implementações de WebView pausam o agendamento de JS pra uma view sem bounds medidos) nem `display:"none"` (pode colapsar layout do mesmo jeito). Remonta via `key` incrementado a cada toque em "Executar" (nunca `injectJavaScript` incremental) — garante que nenhum estado global (uma closure, um contador) sobra de uma tentativa pra outra; reexecutar sempre **limpa** a saída anterior, nunca acumula.
  - **`codeSandboxDocument.ts` faz um `postMessage`** no fim de `buildConsolePanelScript` (depois de montar o painel in-page), postando `{codapTerminal: true, entries, result}` se `window.ReactNativeWebView` existir — é o que o `TerminalSection`, o `CodePlaygroundExercise` e o `CodeEditorExercise` escutam via `onMessage` (`result` é o veredito do `checkScript`, com a lista `checks`; `null` no terminal). **A correção e esse envio ficam no `<head>` e rodam no `DOMContentLoaded`**, cada um no próprio `<script>`: rodam depois do código do aluno, mas fora do caminho dele — um HTML digitado que termina no meio de uma tag (`<input type="email"` sem `>`) engoliria um `<script>` posto depois dele no `<body>`, e a correção nunca rodaria; um erro de sintaxe no `checkScript` também não derruba o envio. O `__codap_report`, o `__codap_check` e o resultado ficam travados (`Object.defineProperty`, resultado numa variável fechada e zerado antes da correção), para o código livre do aluno não burlar a correção, e `</script>`/`</style>` no código são escapados. Posta **sempre**, inclusive sem nenhuma entrada (antes só postava com saída, e o terminal decidia "sem saída" pela janela de graça — o resultado é o mesmo). Fora de uma WebView RN (ou na própria aba "Web", que nunca teve `onMessage`) a chamada é um no-op silencioso. Um único `buildSandboxHtmlDocument()` serve os três usos.
  - **Sem `onShouldStartLoadWithRequest`** (guarda de navegação) — o código aqui é 100% autorado por quem escreve a lição, nunca editável pelo aluno, mesma fronteira de confiança que a aba "Web" já tem (que nunca teve essa guarda). O hardening de código *do aluno* mora no `code_playground` (ver abaixo).
  - **Watchdog de ~4s existe, mas é UX, não segurança**: cobre um loop infinito acidental no conteúdo autorado (erro de digitação, recursão sem caso base), não uma ameaça — mesma janela 3-5s já usada como baseline no roadmap pro `code_playground`. Uma execução sem nenhum `console.log` não é tratada como travamento: `onLoadEnd` + uma janela de graça curta (250ms, só pra cobrir o agendamento síncrono do script) decide "rodou, sem saída" antes do watchdog completo disparar.
  - **Limitação conhecida, não resolvida**: o `postMessage` dispara uma única vez, logo depois do script síncrono do usuário (mais qualquer microtask já resolvida nesse ponto — uma Promise encadeada no mesmo bloco já roda a tempo, por causa do checkpoint de microtasks entre `<script>`s consecutivos). Um `console.log` agendado via `setTimeout` (macrotask) **não** é capturado por esse post único. Nenhuma das ~47 telas elegíveis hoje (as 8 das lições novas de JavaScript incluídas, conferidas executando o código antes de gravar) usa `setTimeout` fora de um contexto que já ganhou aba "Web" própria, mas é uma armadilha real para conteúdo futuro — sinalizar antes de marcar uma lição nova como elegível ao terminal se ela loga algo de dentro de um `setTimeout`.
  - **`terminalCode` cobre dois casos, não só TypeScript** — sempre JS executável a rodar no lugar de `code`/`additionalCode`, quando o que é ensinado não roda direto na sandbox:
    - **TypeScript, pré-transpilado na autoria**: como não há transpiler embarcado no app (mesmo motivo da aba "Web" nunca executar TS), o campo carrega o JS já pronto (gerado uma vez com `ts.transpileModule`, nunca em runtime — todo conteúdo de TS é fixo, nunca editado pelo aluno). Nunca embarcar um transpiler (Sucrase ou equivalente) no app pra isso — pagaria peso de bundle em todo aparelho por um conteúdo que nunca muda; ver `docs/roadmap-atividades-praticas.md` pelo princípio geral ("nenhuma peça depende de motor de execução pesado").
    - **JavaScript "simulado"**: o código **exibido** ao aluno continua fiel ao que é ensinado; só o que executa por trás do botão é diferente. Dois exemplos reais: a lição "Módulos" ensina `export function somar(a, b) {...}` (`export` é `SyntaxError` fora de um módulo ES) — o `terminalCode` é a mesma função sem o `export`, com uma chamada e `console.log` que o código exibido não tem. A lição "HTTP e fetch" ensina `fetch("/api/users");` sozinho — uma chamada de rede de verdade contra uma URL relativa sem servidor atrás falharia ou ficaria pendurada na sandbox — o `terminalCode` define um `fetch` simulado local (`setTimeout` resolvendo `{status: 200}`, nunca sai do dispositivo) e reaproveita a chamada exibida sem alterar nada nela; como o código ensinado não tem `.then()`, o resultado ainda é "Nenhuma saída de console." — o ganho aqui é só provar que a sintaxe roda sem erro, não mostrar um valor.
  - **Sem o campo, a lição continua exatamente como antes** — sem terminal, só o código estático (mesmo efeito de `noTerminal`, mas é o padrão natural: a maioria das lições de TypeScript não produz nenhuma saída de console mesmo transpilada).
  - **`api/prisma/generateTerminalCode.ts`** lê do banco toda atividade `codeLanguage: 'TypeScript'` e imprime um candidato de `terminalCode` (via `ts.transpileModule`) pra revisão humana — **nunca escreve** no banco/seed (mesmo princípio de `checkSeedDrift.ts`). Só cobre o caso de TypeScript — os casos de JavaScript simulado são escritos à mão, um a um, porque cada simulação é uma decisão de conteúdo específica (o que mockar, como), não um padrão mecânico como "apaga os tipos". A aplicação de fato é manual, um script de patch avulso por vez (mesmo padrão dos outros `_patch_*.ts` já usados, descartável) + `pnpm seed:generate` + `pnpm seed:check` + publicar uma `content_version`.
  - **Das 13 atividades de TypeScript do módulo Avançado, só "any e unknown" ganhou `terminalCode` até agora** — é a única cujo código, depois de transpilado, produz alguma saída de `console.log`; as outras 12 ou não logam nada (a maioria — só declarações de tipo, interfaces que somem inteiras na transpilação, generics cujo resultado nunca é impresso) ou, no caso de "Por que TypeScript?", **transpilar mudaria o sentido da lição**: o ponto central é um erro pego em tempo de compilação (`somar(2, "3")` com tipos), e rodado de verdade isso não lança erro nenhum — `+` concatena e vira `"23"`, contradizendo silenciosamente o que o texto ensina. Deixada de fora de propósito, não esquecida. Aumentar essa cobertura mais tarde é um passe de conteúdo (revisar candidato por candidato com `generateTerminalCode.ts`), não uma mudança de mecanismo.
  - **O módulo "Além do JavaScript" (Node.js/Express) ganhou `noTerminal: true` em massa** (22 das 26 atividades) — nenhuma tela dele tinha sido revisada quando o terminal foi criado, e a maior parte usa `import`/`export`/`await` de nível superior ou referencia `process`/`app`/`express` (indefinidos num engine de navegador): sem a flag, "Executar" mostrava um erro de verdade — `SyntaxError` ou `ReferenceError` —, não "sem saída", o que engana o aluno fazendo parecer um erro dele. As 4 atividades deixadas elegíveis ("JavaScript fora do navegador" ×2, "Browser vs Node.js" ×2) não usam nenhuma API exclusiva do Node — rodam limpo, sem precisar de simulação nenhuma.
- **`app/src/utils/tailwindSubset.ts`** centraliza o CSS resolvido das classes utilitárias Tailwind ensinadas no módulo "Além do CSS" (`TAILWIND_SUBSET`, classe → regra) e `resolveTailwindSubsetCss(html)`, que varre `class="..."` no HTML recebido e devolve só as regras das classes presentes no mapa — não é um motor Tailwind (sem JIT, sem CDN, inviável offline), só a versão compartilhada do que antes era resolvido manualmente por lição via `additionalCode` em `api/prisma/seed.ts`. Uma classe ensinada fora do mapa não gera regra (mesma falha silenciosa de antes, não é regressão). As 8 lições que já têm `additionalCode` CSS manual não foram migradas para usar essa função — o arquivo é a fonte de verdade para conteúdo futuro, não uma mudança no conteúdo já seedado.
- **O modal escondido abre segurando o botão "Sobre" em Configurações por 5 segundos** (`ListRow` tem `onLongPress`/`delayLongPress`/`onPressIn`/`onPressOut` opcionais; `Config.tsx` compõe `AboutCodap` + `SecretTestLesson`). O toque normal continua abrindo os créditos — o `TouchableOpacity` só dispara `onPress` no soltar se o `onLongPress` não tiver disparado. **Enquanto "Sobre" está pressionado, a rolagem de Configurações fica travada** (`scrollEnabled={!holdingAbout}`, via `onHoldChange` do `AboutCodap`): no Android, quando a tela tem o que rolar (celular menor, fonte do app aumentada), o `ScrollView` toma o gesto assim que o dedo anda uns 8 dp e cancela o toque longo — e em 5 s um dedo de verdade anda isso. Reproduzido no emulador com a fonte aumentada; com a tela inteira cabendo não acontecia, por isso o gesto parado do `adb` sempre funcionava. O modal rola por dentro, com o cabeçalho e o botão de fechar fixos.
- **Conclusão de lição está plugada**: ao terminar a última atividade, `Lesson.tsx` chama `SyncService.recordLessonCompletion(remoteId, lessonId)` (grava em `UserLessons`/`SyncQueue` na mesma transação e já agenda o flush) — nunca `DatabaseClient.completeLesson` direto, senão o envio para `/sync` não é disparado. `AreaModules` lê `DatabaseClient.getClasses(remoteId)` num `useFocusEffect` para marcar `checked` no `ClassButton` das lições já concluídas, relendo a cada volta para a tela.
- **Removidos** nesta migração: `ScreenJourney.tsx` (dispatcher por string) e as telas `lessons/html/Html.tsx`, `lessons/css/Css.tsx`, `lessons/js/JavaScript.tsx` (cada uma hardcodava os mesmos 4 módulos "em breve", com bastante duplicação entre si) — toda essa responsabilidade foi substituída por `AreaModules.tsx`, data-driven a partir da API.

## Reutilização de componentes

Antes de criar qualquer componente novo em `/app`:
1. Procure primeiro por um componente existente que atenda à necessidade (em `components/themed`, `components/layout`, ou nos `components/` da própria tela em `screens/*/components`).
2. **Sempre reutilize** um componente existente quando ele atender à necessidade. Não duplique, não recrie um componente equivalente, não reimplemente uma funcionalidade já coberta por um componente ou utilitário existente.
3. Se um componente existente precisar de uma nova variação, avalie primeiro evoluí-lo de forma limpa (ex.: nova prop opcional) antes de criar um novo.
4. Evite duas armadilhas opostas:
   - Criar várias cópias quase idênticas de um mesmo componente (`ComponentType1`, `ComponentType2`, ...) só variando um detalhe.
   - Transformar um componente único em um monólito cheio de condicionais para acumular responsabilidades claramente diferentes só para evitar criar um segundo componente.
5. Priorize, nessa ordem de julgamento: reutilização, clareza, manutenibilidade, consistência com os padrões já existentes no projeto (ex.: convenção `Themed*`, layout primitives, discriminação por `type` no conteúdo de aulas), baixo acoplamento e ausência de duplicação desnecessária.

## Comandos

O repositório é um workspace pnpm unificado (ver [CLAUDE.md](../CLAUDE.md) da raiz) — **instale as dependências uma única vez a partir da raiz** (`pnpm install`), nunca dentro de `/app` isoladamente. Os scripts abaixo podem ser rodados de duas formas equivalentes: com `cd app` e o comando direto, ou a partir da raiz com `pnpm --filter codap <script>` (há atalhos prontos em `package.json` da raiz: `app:start`, `app:android`, `app:ios`, `app:web`).

- Iniciar o Metro/Expo (escolher plataforma no menu do CLI): `pnpm start`
- Rodar direto no Android: `pnpm android`
- Rodar direto no iOS: `pnpm ios`
- Rodar na Web: `pnpm web`
- **`.env` precisa de `EXPO_PUBLIC_API_URL`** apontando para a API local/remota (ver `.env.example`); variáveis `EXPO_PUBLIC_*` são inlined pelo Expo em build time.
- **Não há scripts de teste, lint ou typecheck definidos no `package.json`.** Para checar tipos manualmente é possível rodar `npx tsc --noEmit`, mas isso não é um script do projeto — confirme com o desenvolvedor antes de adotar isso como verificação padrão.
